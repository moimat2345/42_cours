C++ · Module 03 · Héritage

CPP03

Faire hériter une classe d'une autre : construire et détruire dans le bon ordre, partager des attributs avec protected, puis démêler un héritage en losange avec virtual.

sujet : en.subject.pdf · version 8.1 · C++98 · c++ -Wall -Wextra -Werror -std=c++98

01

Le module en bref

Tu construis une petite famille de robots. Tout part de ClapTrap : un nom et trois nombres (points de vie, points d'énergie, dégâts d'attaque), avec trois actions : attaquer, encaisser des dégâts, se réparer. Deux classes en héritent, ScavTrap et FragTrap : elles réutilisent tout ce que fait ClapTrap et ajoutent chacune une capacité spéciale. Un dernier exercice, facultatif, te demande un DiamondTrap qui hérite des deux à la fois.

Le module tient en trois idées. D'abord, une classe dérivée contient sa base : la base est construite en premier et détruite en dernier. Ensuite, protected ouvre les attributs de la base aux classes dérivées sans les ouvrir au reste du programme. Enfin, quand deux chemins d'héritage mènent à la même base, il faut virtual pour n'en garder qu'un exemplaire.

💡

Tes messages sont ta preuve. Le sujet veut un message dans chaque action, dans les constructeurs et dans le destructeur (p. 9) : c'est ce qui permet au correcteur de voir l'ordre de construction et de destruction. Écris dans ton main des tests qui les montrent.

03

L'héritage en pratique

Une classe qui en contient une autre

Avec class ScavTrap : public ClapTrap, tu dis qu'un ScavTrap est un ClapTrap avec des choses en plus. Concrètement, un objet ScavTrap contient un sous-objet ClapTrap (la base), puis les membres propres à ScavTrap. C'est l'héritage public, le choix naturel ici (le sujet ne précise pas le mot-clé) : les membres publics de la base restent publics dans la dérivée.

ScavTrap.hpp (l'idée)
class ScavTrap : public ClapTrap
{
    // un ScavTrap contient un ClapTrap, plus ce qu'on écrit ici
};

private, protected, public : qui voit quoi ?

Membre déclaré dans ClapTrapClapTrap lui-mêmeUne classe dérivéeLe reste du programme
private✓ oui✗ non✗ non
protected✓ oui✓ oui✗ non
public✓ oui✓ oui✓ oui

À l'ex00, le sujet donne les attributs de ClapTrap comme privés (p. 8). À l'ex01, ScavTrap doit utiliser ces attributs et le sujet demande de mettre ClapTrap à jour en conséquence (p. 10). Il faut donc ouvrir l'accès aux classes dérivées sans l'ouvrir à tout le monde : c'est exactement le rôle de protected. Si tu oublies, le compilateur te le rappelle : lire un membre private de la base depuis une dérivée donne '_name' is a private member of 'ClapTrap' (constaté avec clang sur macOS).

Construction et destruction : l'ordre à connaître

Quand tu écris ScavTrap robo("Robo");, le programme commence par construire le sous-objet ClapTrap, puis exécute le constructeur de ScavTrap. À la sortie de la portée, c'est l'inverse : le destructeur de ScavTrap d'abord, celui de ClapTrap ensuite. Le sujet te demande de le montrer dans tes tests et pose la question du pourquoi (p. 10).

La réponse tient en une phrase : le corps du constructeur de ScavTrap peut utiliser les attributs de ClapTrap, donc la base doit exister avant lui ; et à la destruction, on défait dans l'ordre inverse pour que le destructeur de la dérivée trouve encore sa base intacte. Essaie les quatre classes :

Démo : choisis une classe parmi ClapTrap, ScavTrap, FragTrap et DiamondTrap, instancie-la, puis sors de la portée. Pour un ScavTrap, les constructeurs s'exécutent dans l'ordre ClapTrap, ScavTrap et les destructeurs dans l'ordre inverse : ScavTrap, ClapTrap. Pour un DiamondTrap (avec virtual), la construction donne ClapTrap, ScavTrap, FragTrap, DiamondTrap, et la destruction suit l'ordre inverse : DiamondTrap, FragTrap, ScavTrap, ClapTrap.

Choisir le constructeur de la base

Dans la liste d'initialisation (après les deux-points), tu dis quel constructeur de la base appeler. Si tu n'écris rien, le compilateur appelle le constructeur par défaut de la base : ton robot ne reçoit donc pas le nom que tu as passé (constaté en compilant et en exécutant : il garde le nom que donne le constructeur par défaut). Avec -Wextra -Werror, le paramètre devenu inutilisé est même refusé (unused parameter), ce qui te prévient.

ScavTrap.cpp (l'idée)
ScavTrap::ScavTrap(const std::string &name) : ClapTrap(name)
{
    // ici, le sous-objet ClapTrap est déjà construit
}

Cacher n'est pas redéfinir

ScavTrap écrit son propre attack, avec un autre message (p. 10). Une fonction de même nom dans la dérivée cache celle de la base. Sans virtual (c'est le sujet du module 04), le choix se fait d'après le type écrit dans le code : appelée sur un ScavTrap, c'est la version de ScavTrap ; appelée à travers un ClapTrap * pointant sur ce même objet, c'est encore celle de ClapTrap (constaté en exécutant). Dans ce module, tu utilises tes objets avec leur vrai type, donc ça suffit.

04

ex00 · ClapTrap

Une classe ClapTrap avec quatre attributs privés (p. 8) : le nom (le paramètre du constructeur), les points de vie (10), les points d'énergie (10) et les dégâts d'attaque (0). Trois fonctions membres publiques, avec ces signatures : void attack(const std::string& target);, void takeDamage(unsigned int amount); et void beRepaired(unsigned int amount);.

Fichiers à rendre (dossier ex00/) : Makefile, main.cpp, ClapTrap.hpp (ou .h) et ClapTrap.cpp (p. 8).

Le header : déclarations seulement

ex00/ClapTrap.hpp
#ifndef CLAPTRAP_HPP
#define CLAPTRAP_HPP

#include <string>

class ClapTrap
{
    private:
        std::string   _name;
        unsigned int  _hitPoints;      // 10 au départ
        unsigned int  _energyPoints;   // 10 au départ
        unsigned int  _attackDamage;   // 0 au départ

    public:
        ClapTrap();
        ClapTrap(const std::string &name);
        ClapTrap(const ClapTrap &other);
        ClapTrap &operator=(const ClapTrap &other);
        ~ClapTrap();

        void attack(const std::string &target);
        void takeDamage(unsigned int amount);
        void beRepaired(unsigned int amount);
};

#endif

Les noms des attributs (_name, _hitPoints…) sont une suggestion : le sujet n'impose aucun nom de variable pour ClapTrap. La forme canonique (constructeur par défaut, de copie, operator=, destructeur) est exigée dès le module 02 (p. 4). Tout le corps des fonctions va dans le .cpp.

Les règles du jeu

ActionPossible siEffetÉnergie
attack(target)au moins 1 point de vie et 1 d'énergiela cible perd autant de points de vie que tes dégâts d'attaque : tu l'annonces dans un message−1
takeDamage(n)le sujet ne le dit pas explicitement (voir p. 8) : à toi de choisirtu perds n points de vie0
beRepaired(n)au moins 1 point de vie et 1 d'énergietu regagnes n points de vie−1

Attaquer et se réparer coûtent chacun 1 point d'énergie, et un ClapTrap ne peut rien faire s'il n'a plus de points de vie ou plus d'énergie (p. 8). Les ClapTrap n'interagissent pas directement : attack reçoit un simple nom (std::string), pas un autre robot, donc elle affiche un message sans toucher personne (p. 8). La règle générale (« ne peut rien faire », p. 8) ne dit pas explicitement si elle vise aussi takeDamage sur un robot déjà à zéro : décide, et sois prêt à justifier ton choix.

Les messages

Chaque fonction membre affiche un message qui décrit ce qui se passe, et les constructeurs et le destructeur aussi (p. 9). Pour attack, le sujet donne ce modèle (sans les chevrons) ; reprends-le tel quel pour être tranquille :

message d'attack (p. 9)
ClapTrap <name> attacks <target>, causing <damage> points of damage!

Les autres messages sont libres. Voici ce que peut afficher un main minimal (exemple : tes messages seront différents) :

sortie d'exemple
ClapTrap Bob constructed
ClapTrap Bob attacks Alice, causing 0 points of damage!
ClapTrap Bob takes 4 damage, hp=6
ClapTrap Bob repairs 3, hp=9 ep=8
ClapTrap Bob destroyed
🧪

Ce que ton main doit prouver. Il est à toi (p. 9). Teste une attaque, des dégâts, une réparation ; puis épuise l'énergie (10 actions), puis fais tomber les points de vie à zéro, et regarde que plus rien ne passe.

07

ex03 · DiamondTrap

🎯

Cet exercice est facultatif. Le sujet indique qu'on peut valider le module sans le faire (p. 13). Il n'emploie pas le mot « bonus ». Si tu le tentes, ses fichiers s'ajoutent à ceux des exercices précédents : DiamondTrap.hpp (ou .h) et DiamondTrap.cpp (p. 12).

Le sujet décrit un monstre : un ClapTrap mi-FragTrap, mi-ScavTrap. DiamondTrap hérite des deux (p. 12). Il a un attribut privé qui porte exactement le même nom de variable que celui de ClapTrap pour le nom du robot (si le tien s'appelle _name dans ClapTrap, appelle-le _name ici aussi). Le ClapTrap intégré porte le nom du paramètre suivi de _clap_name. Les points de vie viennent de FragTrap, l'énergie de ScavTrap, les dégâts de FragTrap, et attack() de ScavTrap. Sa capacité propre est void whoAmI();, qui affiche à la fois son nom et son nom de ClapTrap (p. 12 et 13).

Le problème : deux ClapTrap

ScavTrap contient un ClapTrap, FragTrap aussi. Un DiamondTrap contient donc, par défaut, deux ClapTrap, chacun avec ses points de vie : c'est le schéma en losange, d'où le nom du problème. Le sujet exige l'inverse : le ClapTrap du DiamondTrap est créé une fois et une seule (p. 13). Le mot-clé virtual sur les deux héritages intermédiaires dit au compilateur de ne garder qu'un exemplaire partagé de la base. Bascule l'interrupteur :

Démo : un interrupteur « héritage virtual ». Sans virtual, un DiamondTrap contient deux sous-objets ClapTrap : la construction donne ClapTrap, ScavTrap, ClapTrap, FragTrap, DiamondTrap, et l'accès à ClapTrap::_name est ambigu (le compilateur refuse). Avec virtual, il n'y en a qu'un : la construction donne ClapTrap, ScavTrap, FragTrap, DiamondTrap, et l'ambiguïté disparaît.

Les messages du compilateur de la démo ont été constatés avec clang 17 sur macOS (par exemple ambiguous conversion from derived class 'DiamondTrap' to base class 'ClapTrap'). Le texte exact change d'un compilateur à l'autre, mais le refus est le même : à vérifier avec le c++ de ton école.

Ce qui change dans le code

D'abord, virtual se pose sur les deux héritages de ClapTrap, dans les headers de ScavTrap et de FragTrap. Le comportement d'un ScavTrap seul ne change pas.

ex03/ScavTrap.hpp et ex03/FragTrap.hpp (la modification)
class ScavTrap : virtual public ClapTrap   // et de même pour FragTrap
{
    // ... inchangé ...
};

Ensuite, c'est la classe la plus dérivée, ici DiamondTrap, qui construit la base virtuelle. Les appels à ClapTrap(name) écrits dans les constructeurs de ScavTrap et de FragTrap sont ignorés quand l'objet construit est un DiamondTrap. C'est donc à lui de nommer ClapTrap dans sa liste d'initialisation, avec le nom suivi de _clap_name.

ex03/DiamondTrap.cpp (la ligne qui compte)
DiamondTrap::DiamondTrap(const std::string &name)
    : ClapTrap(name + "_clap_name"), ScavTrap(name), FragTrap(name), _name(name)

Le constructeur de copie obéit à la même règle : s'il ne nomme pas ClapTrap(other), la copie est faite avec le constructeur par défaut de ClapTrap.

Le header de DiamondTrap

ex03/DiamondTrap.hpp
#ifndef DIAMONDTRAP_HPP
#define DIAMONDTRAP_HPP

#include "ScavTrap.hpp"
#include "FragTrap.hpp"

class DiamondTrap : public ScavTrap, public FragTrap
{
    private:
        std::string  _name;   // même nom de variable que dans ClapTrap (consigne du sujet)

    public:
        DiamondTrap();
        DiamondTrap(const std::string &name);
        DiamondTrap(const DiamondTrap &other);
        DiamondTrap &operator=(const DiamondTrap &other);
        ~DiamondTrap();

        using ScavTrap::attack;   // l'attack de ScavTrap, comme le veut le sujet
        void whoAmI();
};

#endif

Deux noms, une seule variable à choisir

Dans DiamondTrap, le nom _name désigne l'attribut du DiamondTrap : il cache celui de ClapTrap. Pour lire le nom du ClapTrap, écris ClapTrap::_name, ce qui suppose que l'attribut soit protected et qu'il n'y ait qu'un seul ClapTrap (la démo ci-dessus). Le sujet te renvoie aux options -Wshadow et -Wno-shadow (p. 13). Avec -Wall -Wextra -Werror, ce nom répété ne provoque aucun avertissement (constaté avec clang 17 sur macOS, même avec -Wshadow). Chez clang, c'est l'option distincte -Wshadow-field qui signale shadows member inherited from type 'ClapTrap'. Comportement du g++ de ton école : à vérifier.

Remarque les 30 points de dégâts : ils viennent de FragTrap, alors que le message d'attack vient de ScavTrap, exactement comme la liste du sujet (p. 12).

09

Pièges classiques

⚠️

Oublier virtual, ou ne le mettre que d'un côté. Sans lui, DiamondTrap contient deux ClapTrap et tout accès à un membre de ClapTrap est ambigu. Il faut virtual sur les deux héritages, ScavTrap et FragTrap : avec un seul des deux, il reste deux sous-objets, et le compilateur refuse toujours l'accès (constaté avec clang sur macOS : found in multiple base-class subobjects of type 'ClapTrap').

⚠️

Ne pas nommer ClapTrap dans le constructeur de DiamondTrap. Avec la base virtuelle, c'est lui qui construit ClapTrap. S'il ne l'appelle pas, c'est le constructeur par défaut qui s'exécute : le nom du ClapTrap n'est pas xxx_clap_name, et rien ne le signale à la compilation (constaté en exécutant). Même piège dans le constructeur de copie.

⚠️

L'ordre des bases dans la liste d'héritage. C'est lui qui fixe l'ordre de construction, pas l'ordre de ta liste d'initialisation. Avec public ScavTrap, public FragTrap, on construit ClapTrap, ScavTrap, FragTrap, puis DiamondTrap ; dans l'autre ordre, FragTrap passe avant ScavTrap. La destruction suit l'ordre inverse. Écris ta liste d'initialisation dans le même ordre que la liste d'héritage : sinon -Wall avertit, et avec -Werror la compilation échoue (constaté avec clang : -Wreorder-ctor).

⚠️

Les valeurs de départ qui se marchent dessus. ScavTrap et FragTrap écrivent chacun leurs valeurs dans le même ClapTrap : le dernier construit gagne. Avec ScavTrap puis FragTrap, tu obtiens 100 / 100 / 30 : l'énergie est celle de FragTrap, alors que le sujet veut celle de ScavTrap (50). Dans l'autre ordre, c'est 100 / 50 / 20 : les dégâts sont ceux de ScavTrap, alors que le sujet veut 30. Dans les deux cas, DiamondTrap doit corriger lui-même ce qui ne convient pas (constaté en exécutant).

⚠️

attack et le using. Le sujet veut l'attack() de ScavTrap (p. 12). Si FragTrap a aussi écrit le sien, d.attack(...) devient ambigu (clang : found in multiple base classes of different types). using ScavTrap::attack; dans DiamondTrap tranche et dit clairement ce que tu veux. Si seul ScavTrap a un attack, l'appel compile déjà avec virtual ; sans virtual, il est ambigu dans tous les cas (constaté avec clang).

⚠️

Le destructeur qui n'est pas virtual. Avec des objets locaux, comme dans ce module, tout va bien. Mais ClapTrap *p = new ScavTrap("S"); delete p; n'exécute que ~ClapTrap : le comportement est formellement indéfini, et avec clang sur macOS le ~ScavTrap n'est pas appelé, sans aucun avertissement avec -Wall -Wextra -Werror. Mettre virtual sur le destructeur de ClapTrap règle le problème (vérifié) ; le sujet de ce module ne l'impose pas, mais c'est une bonne habitude avant le module 04.

⚠️

Les messages que le sujet attend. Un message dans chaque action, dans les constructeurs et dans le destructeur (p. 9) ; ScavTrap change ses messages de constructeurs, de destructeur et d'attack() (p. 10), FragTrap ceux de construction et de destruction (p. 11) ; l'enchaînement doit se voir dans tes tests (p. 10 et 11). Si ton ScavTrap affiche ClapTrap ... attacks, le correcteur croira que l'attack de la dérivée n'est pas appelé. Chaque message finit par un retour à la ligne et va sur la sortie standard (p. 3).

⚠️

Énergie à 0 ou points de vie à 0. Le sujet dit qu'un ClapTrap ne peut rien faire dans ces deux cas (p. 8). Teste les deux séparément : dix attaques puis une onzième (plus d'énergie), puis des dégâts supérieurs aux points de vie (plus de vie), puis une réparation. Dans chaque cas, affiche pourquoi l'action est refusée. N'oublie pas que se réparer coûte aussi 1 point d'énergie.

⚠️

int et unsigned int. Les paramètres amount sont des unsigned int (p. 8). Soustraire 10 à 6 points de vie unsigned int donne 4294967292 : ton robot devient immortel. Avec des int, tu obtiens −4, et if (hp < amount) compare un signé et un non signé : avec -Wextra -Werror, c'est une erreur de compilation (-Wsign-compare). Compare avant de soustraire, ou borne à zéro. Constaté avec clang sur macOS.

⚠️

La partie base oubliée dans la copie. Si l'operator= de la dérivée n'appelle pas ClapTrap::operator=, le nom, les points de vie, l'énergie et les dégâts ne sont pas copiés : après b = a;, b garde son ancien nom (constaté en exécutant). Même idée pour le constructeur de copie, qui doit nommer ClapTrap(other).

10

Comment je l'ai fait

J'ai écrit ClapTrap avec un nom et trois compteurs entiers, privés à l'ex00, puis passés en protected à l'ex01 pour que les classes dérivées y accèdent. Chaque constructeur appelle celui de sa base, pose ses propres valeurs et affiche un message préfixé par le nom de la classe, ce qui rend l'ordre de construction et de destruction lisible dans la sortie. ScavTrap écrit son propre attack avec son message ; FragTrap garde celui de ClapTrap. Avant d'attaquer ou de se réparer, chaque fonction teste les points de vie puis l'énergie et affiche un refus sinon, et takeDamage ne descend jamais sous zéro. Le constructeur de copie et l'affectation passent par ceux de la base. Mon main crée un robot de chaque classe et appelle toutes les actions. Mon dépôt s'arrête à l'ex02 : je n'ai pas fait l'ex03, facultatif.

📌 À retenir (défense d'éval)

  • ✓
    Ordre de construction. La base d'abord, puis la dérivée ; destruction dans l'ordre inverse. Pourquoi : le corps du constructeur de la dérivée utilise la base, et le destructeur de la dérivée doit la trouver intacte.
  • ✓
    protected ou private ? private reste dans la classe, protected s'ouvre aux classes dérivées, public à tout le monde. L'ex01 demande d'ouvrir les attributs de ClapTrap à ScavTrap.
  • ✓
    Valeurs de départ. ClapTrap 10 / 10 / 0 ; ScavTrap 100 / 50 / 20 ; FragTrap 100 / 100 / 30 ; DiamondTrap : vie et dégâts de FragTrap, énergie de ScavTrap (100 / 50 / 30).
  • ✓
    Coûts. attack et beRepaired coûtent 1 énergie ; à zéro point de vie ou zéro énergie, le robot ne fait rien ; takeDamage ne coûte pas d'énergie.
  • ✓
    Choisir le constructeur de la base. Dans la liste d'initialisation ; sinon c'est le constructeur par défaut qui est appelé.
  • ✓
    Cacher n'est pas redéfinir. L'attack de ScavTrap cache celui de ClapTrap ; sans virtual, un ClapTrap * appelle encore celui de ClapTrap. La suite, au module 04.
  • ✓
    Forme canonique. Le constructeur de copie nomme la base, operator= appelle celui de la base, chaque constructeur et chaque destructeur affiche un message.
  • ✓
    Le losange. Sans virtual, deux ClapTrap et des accès ambigus ; avec virtual sur les deux héritages, un seul, construit par DiamondTrap lui-même.
  • ✓
    L'ex03 est facultatif. Le sujet précise qu'on peut valider le module sans lui (p. 13). -Wshadow et -Wno-shadow sont cités dans le sujet.
  • ✓
