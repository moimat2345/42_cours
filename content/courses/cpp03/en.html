C++ · Module 03 · Inheritance

CPP03

Make one class inherit from another: build and destroy in the right order, share attributes with protected, then untangle a diamond inheritance with virtual.

subject: en.subject.pdf · version 8.1 · C++98 · c++ -Wall -Wextra -Werror -std=c++98

01

The module in brief

You build a small family of robots. It all starts with ClapTrap: a name and three numbers (hit points, energy points, attack damage), with three actions: attack, take damage, repair itself. Two classes inherit from it, ScavTrap and FragTrap: they reuse everything ClapTrap does and each adds a special ability. A last, optional exercise asks for a DiamondTrap that inherits from both at once.

The module comes down to three ideas. First, a derived class contains its base: the base is built first and destroyed last. Second, protected opens the base's attributes to derived classes without opening them to the rest of the program. Third, when two inheritance paths lead to the same base, you need virtual to keep a single copy of that base.

💡

Your messages are your proof. The subject wants a message in every action, in the constructors and in the destructor (p. 9): that is how the evaluator sees the construction and destruction order. Write tests in your main that show them.

03

Inheritance in practice

A class that contains another one

With class ScavTrap : public ClapTrap, you are saying that a ScavTrap is a ClapTrap with extra things. Concretely, a ScavTrap object contains a ClapTrap sub-object (the base), followed by the members specific to ScavTrap. This is public inheritance, the natural choice here (the subject does not specify the keyword): the base's public members stay public in the derived class.

ScavTrap.hpp (the idea)
class ScavTrap : public ClapTrap
{
    // a ScavTrap contains a ClapTrap, plus whatever you write here
};

private, protected, public: who sees what?

Member declared in ClapTrapClapTrap itselfA derived classThe rest of the program
private✓ yes✗ no✗ no
protected✓ yes✓ yes✗ no
public✓ yes✓ yes✓ yes

In ex00, the subject gives ClapTrap's attributes as private (p. 8). In ex01, ScavTrap has to use those attributes, and the subject asks you to update ClapTrap accordingly (p. 10). So you have to open access to derived classes without opening it to everyone: that is exactly what protected is for. If you forget, the compiler reminds you: reading a private member of the base from a derived class gives '_name' is a private member of 'ClapTrap' (observed with clang on macOS).

Construction and destruction: the order to know

When you write ScavTrap robo("Robo");, the program first builds the ClapTrap sub-object, then runs the ScavTrap constructor. When the scope ends, it is the reverse: the ScavTrap destructor first, then the ClapTrap one. The subject asks you to show this in your tests and asks you to explain why (p. 10).

The answer fits in one sentence: the body of the ScavTrap constructor can use ClapTrap's attributes, so the base must exist before it; and on destruction, things are undone in reverse so the derived destructor still finds its base intact. Try all four classes:

Demo: pick a class among ClapTrap, ScavTrap, FragTrap and DiamondTrap, instantiate it, then leave the scope. For a ScavTrap, the constructors run in the order ClapTrap, ScavTrap and the destructors in the reverse order: ScavTrap, ClapTrap. For a DiamondTrap (with virtual), construction gives ClapTrap, ScavTrap, FragTrap, DiamondTrap, and destruction follows the reverse order: DiamondTrap, FragTrap, ScavTrap, ClapTrap.

Choosing the base's constructor

In the initializer list (after the colon), you say which base constructor to call. If you write nothing, the compiler calls the base's default constructor: your robot does not get the name you passed (observed by compiling and running: it keeps the name the default constructor gives it). With -Wextra -Werror, the parameter that is now unused is even rejected (unused parameter), which warns you.

ScavTrap.cpp (the idea)
ScavTrap::ScavTrap(const std::string &name) : ClapTrap(name)
{
    // here, the ClapTrap sub-object is already built
}

Hiding is not overriding

ScavTrap writes its own attack, with a different message (p. 10). A function with the same name in the derived class hides the base's. Without virtual (that is module 04's topic), the choice is made from the type written in the code: called on a ScavTrap, you get the ScavTrap version; called through a ClapTrap * pointing at that same object, you still get ClapTrap's (observed by running it). In this module, you use your objects with their real type, so that is enough.

ex00 · ClapTrap

A ClapTrap class with four private attributes (p. 8): the name (the constructor's parameter), the hit points (10), the energy points (10) and the attack damage (0). Three public member functions, with these signatures: void attack(const std::string& target);, void takeDamage(unsigned int amount); and void beRepaired(unsigned int amount);.

Files to submit (directory ex00/): Makefile, main.cpp, ClapTrap.hpp (or .h) and ClapTrap.cpp (p. 8).

The header: declarations only

ex00/ClapTrap.hpp
#ifndef CLAPTRAP_HPP
#define CLAPTRAP_HPP

#include <string>

class ClapTrap
{
    private:
        std::string   _name;
        unsigned int  _hitPoints;      // 10 at the start
        unsigned int  _energyPoints;   // 10 at the start
        unsigned int  _attackDamage;   // 0 at the start

    public:
        ClapTrap();
        ClapTrap(const std::string &name);
        ClapTrap(const ClapTrap &other);
        ClapTrap &operator=(const ClapTrap &other);
        ~ClapTrap();

        void attack(const std::string &target);
        void takeDamage(unsigned int amount);
        void beRepaired(unsigned int amount);
};

#endif

The attribute names (_name, _hitPoints…) are a suggestion: the subject does not impose any variable name for ClapTrap. The canonical form (default constructor, copy constructor, operator=, destructor) is required from module 02 on (p. 4). The whole body of the functions goes in the .cpp.

The rules of the game

ActionPossible ifEffectEnergy
attack(target)at least 1 hit point and 1 energy pointthe target loses as many hit points as your attack damage: you announce it in a message−1

Attacking and repairing each cost 1 energy point, and a ClapTrap can do nothing once it has no hit points or no energy left (p. 8). The general rule (“can’t do anything”, p. 8) does not say explicitly whether it also covers takeDamage on a robot already at zero: decide, and be ready to justify your choice.

ex03 · DiamondTrap

🎯

This exercise is optional. The subject says you can pass the module without doing it (p. 13). It never uses the word “bonus”. If you try it, its files are added to those of the previous exercises: DiamondTrap.hpp (or .h) and DiamondTrap.cpp (p. 12).

The subject describes a monster: a ClapTrap that is half FragTrap, half ScavTrap. DiamondTrap inherits from both (p. 12). It has a private attribute with exactly the same variable name as ClapTrap's for the robot's name (if yours is called _name in ClapTrap, call it _name here too). The embedded ClapTrap carries the parameter's name followed by _clap_name. Hit points come from FragTrap, energy from ScavTrap, damage from FragTrap, and attack() from ScavTrap. Its own ability is void whoAmI();, which prints both its name and its ClapTrap name (p. 12 and 13).

The problem: two ClapTraps

ScavTrap contains a ClapTrap, and so does FragTrap. A DiamondTrap therefore contains, by default, two ClapTrap, each with its own hit points: that is the diamond shape, hence the name of the problem. The subject demands the opposite: the DiamondTrap's ClapTrap is created once, and only once (p. 13). The virtual keyword on the two intermediate inheritances tells the compiler to keep a single shared copy of the base. Flip the switch:

Demo: a “virtual inheritance” switch. Without virtual, a DiamondTrap contains two ClapTrap sub-objects: construction gives ClapTrap, ScavTrap, ClapTrap, FragTrap, DiamondTrap, and access to ClapTrap::_name is ambiguous (the compiler rejects it). With virtual, there is only one: construction gives ClapTrap, ScavTrap, FragTrap, DiamondTrap, and the ambiguity disappears.

The compiler messages behind the demo were observed with clang 17 on macOS (for example ambiguous conversion from derived class 'DiamondTrap' to base class 'ClapTrap'). The exact wording changes from one compiler to another, but the rejection is the same: to check with your school's c++.

What changes in the code

First, virtual goes on both inheritances of ClapTrap, in the ScavTrap and FragTrap headers. The behavior of a lone ScavTrap does not change.

ex03/ScavTrap.hpp and ex03/FragTrap.hpp (the change)
class ScavTrap : virtual public ClapTrap   // and the same for FragTrap
{
    // ... unchanged ...
};

Second, it is the most derived class, here DiamondTrap, that builds the virtual base. The ClapTrap(name) calls written in the ScavTrap and FragTrap constructors are ignored when the object being built is a DiamondTrap. So it is up to it to name ClapTrap in its initializer list, with the name followed by _clap_name.

ex03/DiamondTrap.cpp (the line that matters)
DiamondTrap::DiamondTrap(const std::string &name)
    : ClapTrap(name + "_clap_name"), ScavTrap(name), FragTrap(name), _name(name)

The copy constructor follows the same rule: if it does not name ClapTrap(other), the copy is built with ClapTrap's default constructor.

DiamondTrap's header

ex03/DiamondTrap.hpp
#ifndef DIAMONDTRAP_HPP
#define DIAMONDTRAP_HPP

#include "ScavTrap.hpp"
#include "FragTrap.hpp"

class DiamondTrap : public ScavTrap, public FragTrap
{
    private:
        std::string  _name;   // same variable name as in ClapTrap (the subject's instruction)

    public:
        DiamondTrap();
        DiamondTrap(const std::string &name);
        DiamondTrap(const DiamondTrap &other);
        DiamondTrap &operator=(const DiamondTrap &other);
        ~DiamondTrap();

        using ScavTrap::attack;   // ScavTrap's attack, as the subject wants
        void whoAmI();
};

#endif

Two names, one variable to pick

Inside DiamondTrap, the name _name refers to the DiamondTrap's own attribute: it hides ClapTrap's. To read the ClapTrap's name, write ClapTrap::_name, which requires the attribute to be protected and requires that there is only one ClapTrap (the demo above). The subject points you to the -Wshadow and -Wno-shadow options (p. 13). With -Wall -Wextra -Werror, this repeated name triggers no warning (observed with clang 17 on macOS, even with -Wshadow). In clang, it is the separate -Wshadow-field option that reports shadows member inherited from type 'ClapTrap'. Behavior of your school's g++: to check.

09

Classic pitfalls

⚠️

Forgetting virtual, or putting it on one side only. Without it, DiamondTrap contains two ClapTrap and any access to a ClapTrap member is ambiguous. You need virtual on both inheritances, ScavTrap and FragTrap: with only one of them, two sub-objects remain, and the compiler still rejects the access (observed with clang on macOS: found in multiple base-class subobjects of type 'ClapTrap').

⚠️

Not naming ClapTrap in DiamondTrap's constructor. With the virtual base, it is DiamondTrap that builds ClapTrap. If it does not call it, the default constructor runs: the ClapTrap's name is not xxx_clap_name, and nothing flags it at compile time (observed by running it). Same trap in the copy constructor.

⚠️

The order of the bases in the inheritance list. It is what sets the construction order, not the order of your initializer list. With public ScavTrap, public FragTrap, you build ClapTrap, ScavTrap, FragTrap, then DiamondTrap; in the other order, FragTrap comes before ScavTrap. Destruction follows the reverse order. Write your initializer list in the same order as the inheritance list: otherwise -Wall warns, and with -Werror the build fails (observed with clang: -Wreorder-ctor).

⚠️

Starting values stepping on each other. ScavTrap and FragTrap each write their values into the same ClapTrap: the last one built wins. With ScavTrap then FragTrap, you get 100 / 100 / 30: the energy is FragTrap's, while the subject wants ScavTrap's (50). In the other order, it is 100 / 50 / 20: the damage is ScavTrap's, while the subject wants 30. Either way, DiamondTrap has to fix by itself whatever does not fit (observed by running it).

⚠️

attack and the using. The subject wants ScavTrap's attack() (p. 12). If FragTrap also wrote its own, d.attack(...) becomes ambiguous (clang: found in multiple base classes of different types). using ScavTrap::attack; in DiamondTrap settles it and states clearly what you want. If only ScavTrap has an attack, the call already compiles with virtual; without virtual, it is ambiguous in every case (observed with clang).

⚠️

The destructor that is not virtual. With local objects, as in this module, everything is fine. But ClapTrap *p = new ScavTrap("S"); delete p; only runs ~ClapTrap: the behavior is formally undefined, and with clang on macOS ~ScavTrap is not called, with no warning at all under -Wall -Wextra -Werror. Putting virtual on ClapTrap's destructor fixes it (verified); the subject of this module does not require it, but it is a good habit before module 04.

⚠️

The messages the subject expects. A message in every action, in the constructors and in the destructor (p. 9); ScavTrap changes the messages of its constructors, destructor and attack() (p. 10), FragTrap those of construction and destruction (p. 11); the chaining must be visible in your tests (p. 10 and 11). If your ScavTrap prints ClapTrap ... attacks, the evaluator will think the derived attack is not being called. Every message ends with a newline and goes to the standard output (p. 3).

⚠️

Energy at 0 or hit points at 0. The subject says a ClapTrap can do nothing in either case (p. 8). Test both separately: ten attacks then an eleventh (no more energy), then damage greater than the hit points (no more life), then a repair. In each case, print why the action is refused. Do not forget that repairing yourself also costs 1 energy point.

⚠️

int and unsigned int. The amount parameters are unsigned int (p. 8). Subtracting 10 from 6 unsigned int hit points gives 4294967292: your robot becomes immortal. With int, you get −4, and if (hp < amount) compares a signed and an unsigned value: with -Wextra -Werror, that is a compile error (-Wsign-compare). Compare before subtracting, or clamp to zero. Observed with clang on macOS.

⚠️

The base part forgotten in the copy. If the derived class's operator= does not call ClapTrap::operator=, the name, hit points, energy and damage are not copied: after b = a;, b keeps its old name (observed by running it). Same idea for the copy constructor, which must name ClapTrap(other).

10

How I did it

I wrote ClapTrap with a name and three integer counters, private in ex00, then made protected in ex01 so the derived classes can reach them. Each constructor calls its base's, sets its own values and prints a message prefixed with the class name, which makes the construction and destruction order readable in the output. ScavTrap writes its own attack with its own message; FragTrap keeps ClapTrap's. Before attacking or repairing, each function checks hit points, then energy, and prints a refusal otherwise, and takeDamage never goes below zero. The copy constructor and the assignment operator go through the base's. My main creates one robot of each class and calls every action. My repository stops at ex02: I did not do ex03, which is optional.

📌 Key takeaways (evaluation defense)

  • ✓
    Construction order. The base first, then the derived class; destruction in the reverse order. Why: the derived constructor's body uses the base, and the derived destructor must find it intact.
  • ✓
    protected or private? private stays in the class, protected opens to derived classes, public to everyone. ex01 asks you to open ClapTrap's attributes to ScavTrap.
  • ✓
    Starting values. ClapTrap 10 / 10 / 0; ScavTrap 100 / 50 / 20; FragTrap 100 / 100 / 30; DiamondTrap: hit points and damage from FragTrap, energy from ScavTrap (100 / 50 / 30).
  • ✓
    Costs. attack and beRepaired cost 1 energy; at zero hit points or zero energy, the robot does nothing; takeDamage costs no energy.
  • ✓
    Choosing the base's constructor. In the initializer list; otherwise the default constructor is called.
  • ✓
    Hiding is not overriding. ScavTrap's attack hides ClapTrap's; without virtual, a ClapTrap * still calls ClapTrap's. The rest comes in module 04.
  • ✓
    Canonical form. The copy constructor names the base, operator= calls the base's, every constructor and destructor prints a message.
  • ✓
    The diamond. Without virtual, two ClapTrap and ambiguous accesses; with virtual on both inheritances, just one, built by DiamondTrap itself.
  • ✓
    ex03 is optional. The subject says you can pass the module without it (p. 13). -Wshadow and -Wno-shadow are mentioned in the subject.
  • ✓
    Submission. c++ -Wall -Wextra -Werror -std=c++98, canonical form, no implementation in a header, include guards, no using namespace or friend, no STL, no leaks, one file per class.
  • ✓
    You may be asked for a small modification. The subject says the defense may occasionally include a small behavior change or a few lines of code to write (p. 14), if the evaluation guidelines mention it. Practice changing a starting value or a message without breaking the construction order.
