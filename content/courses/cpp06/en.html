C++ · Module 06 · Casts

C++ casts

Converting one type into another is fine, as long as you say which cast and why. This course explains the module's three exercises and, above all, the choice of cast you will have to defend.

subject: en.subject-8.pdf · version 8.1 · C++98 · -Wall -Wextra -Werror

01

The module in short

Module 06 revolves around one idea: converting a value from one type to another with the right tool. Three exercises:

ex00: write ScalarConverter, a class that cannot be instantiated, whose only static method convert receives a literal as a string (0, 42.0f, nan, 'c'...) and prints it as a char, an int, a float and a double.

ex01: Serializer, which turns the address of a Data object into a uintptr_t integer, then gets the pointer back.

ex02: given a pointer or a reference to Base, print the real type of the object (A, B or C), without the typeinfo header.

The module adds a rule of its own (p. 6): for each exercise, the type conversion must go through a specific type of cast, and that choice is reviewed during the defense. The subject does not say which cast goes with which exercise: it is up to you to choose one and to be able to justify it.

📖

The page numbers in parentheses, like (p. 6), are the ones printed at the bottom of the subject's pages (version 8.1): the printed page is the PDF page minus one, because the cover is not numbered. Keep the PDF open next to this page: this course explains the subject, it does not replace it.

💡

What you will defend is not "it works". It is "I picked static_cast here because...". A C-style cast almost always compiles, but it does not answer that question: the next section helps you answer it.

03

The four casts

A cast is a conversion written explicitly. In C there is only one, (type)value, and it does everything. In C++ there are four, each with a precise intent: the compiler checks what it can, and whoever reads your code immediately sees what you meant. A grep _cast finds them all.

CastWhat it guarantees, what it checksTypical use
static_cast<T>(x)A conversion between compatible types, checked at compile time: numbers (int, float, double, char), pointer to void *, going up or down a class hierarchy. It refuses pointer to integer, and two pointers to classes with no inheritance link. Nothing is checked at run time: going down to the wrong type gives a bogus pointer.static_cast<int>(3.9) gives 3
reinterpret_cast<T>(x)Reads the same bits as another type: pointer to integer and back, pointer to unrelated pointer. No value conversion (reinterpret_cast<int>(4.2f) does not compile), no run-time check. It refuses to remove a const, or to store a pointer in an integer that is too small.reinterpret_cast<uintptr_t>(ptr)
dynamic_cast<T>(x)Checks at run time, using the real type of the object, that a pointer or a reference to a base class really designates a T. Requires a polymorphic class (at least one virtual function). On failure: a pointer gives NULL, a reference throws std::bad_cast.dynamic_cast<B *>(basePtr)
const_cast<T>(x)Adds or removes const (or volatile), nothing else: const_cast<long *> of a const int * is refused. Writing to an object that was defined const is still undefined behavior, according to the standard.No exercise of the module needs it

Why not stick with the C-style cast? Because it tries everything: static_cast, then reinterpret_cast, and it can even remove a const, silently and with no name to search for. Observed with clang and -Wall -Wextra -Werror: (Data *)raw (an integer read as a pointer) and (char *)constPtr compile without a single warning, and (A *)p on an object that is really a B returns a non-null pointer, with no check at all.

Here is the classic choice for this module. The subject does not require it: it is the answer you must be able to argue.

04

ex00 · ScalarConverter

Your class receives a string that represents a C++ literal in its most common form (p. 9), works out which type it is, then prints its value as the four scalar types. It stores nothing: a single static method, no object.

Files to submit (p. 9): Makefile, ScalarConverter.hpp, ScalarConverter.cpp and your test program main.cpp (see the note on names in the previous section). The subject does not fix the type of the parameter of convert: a const std::string & is a simple choice.

ScalarConverter.hpp
#ifndef SCALARCONVERTER_HPP
# define SCALARCONVERTER_HPP

# include <string>

class ScalarConverter
{
	public:
		static void	convert(const std::string &literal);

	private:
		ScalarConverter();                                    // the four canonical members are private:
		ScalarConverter(const ScalarConverter &other);        // nobody can create, copy
		ScalarConverter &operator=(const ScalarConverter &other); // or destroy a ScalarConverter
		~ScalarConverter();
};

#endif

The work happens in three steps. The subject describes them like this (p. 11): detect the type of the literal, convert it from the string to its real type, then explicitly convert it to the three other types and display the results.

1. Detect the type. The subject gives examples; how to recognize each form is up to you (this table is advice). Do the pseudo-literals first.

char'c', 'a' (p. 9)Three characters: an apostrophe, a displayable character, an apostrophe.
int0, -42, 42 (p. 9)An optional sign, then digits only.
float0.0f, -4.2f, 4.2f (p. 9)An optional sign, digits, a single dot, digits, then f.
double0.0, -4.2, 4.2 (p. 10)Like the float, without the f.

Except for chars, only the decimal notation is used (p. 9): no exponent (1e3), no hexadecimal (0x10). And non-displayable characters will not be given as input (p. 9). Everything else is invalid input: it is up to you to decide what to print, but never to crash.

2. Convert. To go from the string to a number, the subject authorizes "any function" that converts a string to an int, a float or a double (p. 9), such as strtod. That is not a cast: it is text parsing, and it is the part with traps (see the pitfalls). Then going from one numeric type to another is where the cast comes in: static_cast. But a cast does not say "impossible": it is up to you to test the range before casting. The subject asks for a message when a conversion makes no sense or overflows, and tells you to include the headers for numeric limits and special values (p. 11).

3. Display. Four lines, in this order. The words Non displayable and impossible come from the subject's examples (p. 11); the rest of the table is this course's choice.

05

ex01 · Serializer

A pointer is an address, so it is a number. uintptr_t is an unsigned integer type big enough to hold one. Your class has two static methods: serialize reads the address as an integer, deserialize reads that integer back as an address. Nothing is copied: the Data object stays where it is.

Files to submit (p. 12): Makefile, Serializer.hpp, Serializer.cpp, Data.hpp (and Data.cpp if you need it) and main.cpp. The subject reminds you not to forget the Data files.

Serializer.hpp
#ifndef SERIALIZER_HPP
# define SERIALIZER_HPP

# include <stdint.h>
# include "Data.hpp"

class Serializer
{
	public:
		static uintptr_t	serialize(Data *ptr);
		static Data			*deserialize(uintptr_t raw);

	private:
		Serializer();
		Serializer(const Serializer &other);
		Serializer &operator=(const Serializer &other);
		~Serializer();
};

#endif
Data.hpp
#ifndef DATA_HPP
# define DATA_HPP

# include <string>

struct Data
{
	std::string	name;
	int			value;
};

#endif

The cast. The classic choice is reinterpret_cast in both directions: you do not convert a value, you read an address again. static_cast is refused for that, as seen in the previous section. For uintptr_t, include <stdint.h>: it compiles with -std=c++98. <cstdint> is C++11; clang on macOS accepts it in C++98 mode too (observed), but check with your school's compiler.

The test (p. 12). Create a Data with data members, pass its address to serialize, give the result to deserialize, then check that the pointer you get is equal to the original, using == on the two Data *. Also print the integer in decimal and in hexadecimal: it speaks for itself during the defense.

🎲

A real address is never the same twice. Observed on macOS: two runs of the same program print two different stack addresses (0x16d216558 then 0x16b2e2558). So do not try to compare your output to a fixed value. On this machine, sizeof(uintptr_t) and sizeof(void *) are 8, sizeof(unsigned int) is 4: storing an address in an unsigned int is refused (see the previous table).

The demo uses a simulated address, to always show the same digits. Press serialize(ptr), then deserialize(raw): the pointer is the same. Add 1 to the integer: the pointer changes, and the verdict turns false.

Demo: a fake Data object at the simulated address 0x7ffee3b2a1c0. serialize(ptr) returns the integer 140732718555584 (0x7ffee3b2a1c0 in hexadecimal); deserialize(raw) gives back the same address, so ptr == deserialize(serialize(ptr)) is true. With the integer plus 1, that is 140732718555585, you get 0x7ffee3b2a1c1: a different pointer, which must never be dereferenced.

ex02 · Identify real type

You have a pointer (or a reference) to Base, but the object may be an A, a B or a C. How do you tell which, without typeid? By asking dynamic_cast: it compares the real type of the object with the one you propose, and answers yes or no at run time.

Files to submit (p. 13): Makefile, Base.hpp and Base.cpp, A.hpp, B.hpp, C.hpp, a file for generate and identify (you name it), and main.cpp. Why a Base.cpp? Because a function body in a header, even a bare {} after the destructor, is a function implementation in a header: the subject gives 0 (p. 4). Do not take that risk.

Base.hpp
#ifndef BASE_HPP
# define BASE_HPP

class Base
{
	public:
		virtual ~Base();   // the only member: public and virtual (p. 13)
};

#endif
A.hpp
#ifndef A_HPP
# define A_HPP

# include "Base.hpp"

class A : public Base {};   // empty: B and C are identical

#endif

Why the virtual destructor? Because dynamic_cast only accepts polymorphic types: a class with at least one virtual function. Without virtual, the compiler answers "'Base' is not polymorphic" (observed). And destroying an A through a Base * without a virtual destructor is undefined behavior.

generate. It randomly creates an A, a B or a C with new and returns it as a Base *; the subject leaves the random choice up to you (p. 13). Who does the delete? Whoever called generate. Seed the generator only once, in main (see the pitfalls).

identify(Base *p). Try a dynamic_cast to each type: a pointer of the wrong type gives NULL, and the first non-null result gives you the answer.

identify(Base &p). Same idea, but the subject forbids pointers inside this function (p. 13). A reference cannot be "nothing": a failing dynamic_cast to a reference does not return NULL, it throws an exception (std::bad_cast, whose what() returns std::bad_cast here). So you need a try / catch. The trap: std::bad_cast is declared in <typeinfo>, the header the subject forbids you to include (p. 13). Catch std::exception instead, which comes from <exception>: observed, it compiles and works without ever including <typeinfo>.

What the demo does: a chain of attempts, A first, then B, then C, stopped at the first success. For an object of type A, one attempt is enough; for a C, two failures come before the success.

Demo: an object whose real type is hidden. For an object of type B: pointer version, dynamic_cast<A *> returns NULL, dynamic_cast<B *> returns a valid pointer and the function prints B; reference version, dynamic_cast<A &> throws std::bad_cast, dynamic_cast<B &> succeeds and the function prints B. For A, the first attempt succeeds; for C, the first two fail.

❓

And a bare Base? generate never produces one, and the subject only asks for A, B or C (p. 13). But nothing stops you from calling identify on a new Base: observed, all three attempts fail. Plan what your functions do in that case (a message, or nothing), so you are never surprised during the defense.

08

Classic pitfalls

⚠️

nanf or nan? The six pseudo-literals are exact strings (p. 9-10), to recognize before anything else. When printing, std::cout writes nan, inf and -inf (observed): the f of the float line and the + are up to you. To build these values, <limits> provides quiet_NaN() and infinity() in std::numeric_limits<double>.

⚠️

-0.0. Negative zero exists. With std::fixed and std::setprecision(1), -0.0 prints as -0.0 (observed); without fixed, as -0. The subject does not test it: decide the result of your four lines (here: Non displayable, 0, -0.0f, -0.0) and stay consistent.

⚠️

42f is not 42.0f. A float is written with a dot. In C++, float f = 42f; does not even compile (clang: "invalid digit 'f' in decimal constant"). Your detector must reject 42f.

⚠️

A badly closed apostrophe. 'a, 'ab' and '' are not chars: reject them. And the shell eats apostrophes (see the ex00 section): decide what your program does with a lone character like c.

⚠️

strtod accepts much more than the subject. Observed: strtod("42abc") returns 42 and only endptr points at abc; a leading space is accepted; "0x10" gives 16, "1e3" gives 1000; "inf", "infinity" and "NaN" go through too. So validate the shape of the string first, and check endptr. atoi("abc") returns 0, just like atoi("0"): there is no way to tell the error. Finally std::stod, std::stof and std::stoi are C++11, which is forbidden (p. 3): clang on macOS still compiles them with -std=c++98 (observed), so do not trust your local compiler; check with your school's.

⚠️

An int out of range. Converting a double whose truncated value does not fit in an int is undefined behavior according to the standard. The result is not guaranteed: static_cast<int>(3e10) may give 2147483647 or some other value, depending on the machine, the compiler and optimization. Test the range before casting, with the limits from <climits> or <limits>. Same logic for char: static_cast<char>(321) gives 'A' (observed), without warning you.

⚠️

Non-displayable characters. Codes 0 to 31 and 127 give Non displayable. std::isprint (<cctype>) accepts codes 32 to 126, that is 95 characters (observed, "C" locale), but expects a value between 0 and 255: do not pass it a negative char. For 128 to 255, char is signed here (CHAR_MIN is -128) and static_cast<char>(200) is -56: the subject does not settle it, this course prints impossible.

⚠️

"Not instantiable" = the four private members. A private default constructor is enough to stop ScalarConverter s;, but the OCF also asks for the copy constructor, the assignment operator and the destructor: declare all four private. Observed: the compiler answers "calling a private constructor of class 'ScalarConverter'" then "variable of type 'ScalarConverter' has private destructor". Same for Serializer.

⚠️

The wrong cast in the defense. reinterpret_cast to go from a float to an int: refused, it does not convert values. static_cast for a pointer to an integer: refused. A C-style cast everywhere: it compiles, but you did not choose. Prepare one sentence per exercise, as in step 1.

⚠️

Compare the pointers, not the contents. The ex01 test asks for the returned pointer to equal the original (p. 12): == on two Data *, not a comparison of the fields. If you store the address in a type that is too small (unsigned int), the compiler refuses; uintptr_t comes from <stdint.h>. And never hard-code an address in your test: it changes at every run.

⚠️

identify(Base &) with no pointer and no typeinfo. Do not take the address of the reference: the subject forbids it (p. 13). A failing dynamic_cast on a reference throws an exception: you need a try / catch. Do not write typeid: clang answers "you need to include <typeinfo> before using the 'typeid' operator" (observed), and the subject forbids it. To catch the exception without <typeinfo>, use std::exception (<exception>). With libc++ (clang, macOS), even catch (const std::bad_cast &) compiles with only <exception> (observed): do not count on it elsewhere.

⚠️

The forgotten virtual on ~Base. Without a virtual function, dynamic_cast no longer compiles ("'Base' is not polymorphic"), and deleting a derived object through a Base * becomes undefined behavior. Do not write the destructor body in the header either (p. 4).

⚠️

srand inside generate. If you seed the generator on every call with time(NULL), every object created during the same second has the same type: observed, twelve calls in a row all gave the same type (C). Call srand only once, in main.

09

How I did it

I kept the three exercises simple. For ScalarConverter, the four canonical members are private. One function detects the literal's type by hand, pseudo-literals first, then char, int, float and double. The value then goes through a single double, and each output line checks its range before using static_cast. I print one decimal when the number is whole, and the default precision otherwise. Serializer has only two static methods using reinterpret_cast, tried on a Data object from the stack and then from the heap. For exercise 02, the pointer version chains the dynamic_casts and checks whether they return NULL, while the reference version tries them inside try blocks that catch std::exception, never including <typeinfo>. I also tested with a bare Base.

📌 To remember (defense)

  • ✓
    One specific cast per exercise (p. 6). Be able to say which and why: static_cast for numeric conversions, reinterpret_cast for pointer and integer, dynamic_cast for the real type.
  • ✓
    Why not the C-style cast? It mixes everything, removes const without a word and cannot be searched for. C++ casts state the intent, and the compiler refuses nonsense.
  • ✓
    What each cast checks. static_cast: related types, at compile time. reinterpret_cast: almost nothing. dynamic_cast: the real type, at run time, on polymorphic types. const_cast: only const.
  • ✓
    ex00. Detect, convert, display. A cast does not warn you about overflow: test the range first. impossible (nan, infinity, out of range) and Non displayable (0 to 31 and 127) are two different messages.
  • ✓
    The pseudo-literals. -inff +inff nanf -inf +inf nan, six exact strings. At least one decimal: 0.0f, 42.0.
  • ✓
    Not instantiable. The four canonical members private; ScalarConverter s; must not compile.
  • ✓
    ex01. reinterpret_cast in both directions with uintptr_t (<stdint.h>); the test compares two pointers with ==. Nothing is copied.
  • ✓
    ex02. Public virtual destructor in Base, defined in a .cpp. Pointer: dynamic_cast returns NULL. Reference: it throws std::bad_cast, caught through std::exception. No typeinfo, no pointer inside identify(Base &).
  • ✓
    General rules. C++98, -Wall -Wextra -Werror, no *printf or *alloc, no using namespace or friend, include guards, nothing implemented in a header, no leaks.
  • ✓
    Prepare for the small modification (p. 14). It can concern any line of your code: know how to redo a test or change an output quickly.
