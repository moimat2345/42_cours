C++ · Module 06 · Casts

Les casts du C++

Convertir un type en un autre, oui, mais en disant lequel et pourquoi. Ce cours explique les trois exercices du module et, surtout, le choix du cast que tu devras défendre.

sujet : en.subject-8.pdf · version 8.1 · C++98 · -Wall -Wextra -Werror

01

Le module en bref

Le module 06 tourne autour d'une idée : convertir une valeur d'un type vers un autre en choisissant le bon outil. Trois exercices :

ex00 : écrire ScalarConverter, une classe qu'on ne peut pas instancier, dont l'unique méthode statique convert reçoit un littéral sous forme de chaîne (0, 42.0f, nan, 'c'…) et l'affiche en char, int, float et double.

ex01 : Serializer, qui transforme l'adresse d'un objet Data en entier uintptr_t, puis retrouve le pointeur.

ex02 : à partir d'un pointeur ou d'une référence sur Base, afficher le vrai type de l'objet (A, B ou C), sans l'en-tête typeinfo.

Le module ajoute une règle qui lui est propre (p. 6) : pour chaque exercice, la conversion de type doit passer par un type de cast précis, et ce choix est examiné en défense. Le sujet ne dit pas quel cast va avec quel exercice : c'est à toi de le choisir et de savoir le justifier.

03

Les quatre casts

Un cast est une conversion écrite explicitement. En C, il n'y en a qu'un, (type)valeur, et il fait tout. En C++, il y en a quatre, chacun avec une intention précise : le compilateur vérifie ce qu'il peut, et celui qui relit ton code voit tout de suite ce que tu voulais. Un grep _cast les retrouve tous.

CastCe qu'il garantit, ce qu'il vérifieCas typique
static_cast<T>(x)Une conversion entre types compatibles, vérifiée à la compilation : nombres (int, float, double, char), pointeur vers void *, remonter ou descendre une hiérarchie de classes. Il refuse pointeur vers entier, et deux pointeurs de classes sans lien d'héritage. Rien n'est vérifié à l'exécution : descendre vers le mauvais type donne un pointeur faux.static_cast<int>(3.9) donne 3
reinterpret_cast<T>(x)Relit les mêmes bits comme un autre type : pointeur vers entier et l'inverse, pointeur vers pointeur sans lien. Aucune conversion de valeur (reinterpret_cast<int>(4.2f) ne compile pas), aucune vérification à l'exécution. Il refuse de retirer un const, ou de ranger un pointeur dans un entier trop petit.reinterpret_cast<uintptr_t>(ptr)
dynamic_cast<T>(x)Vérifie à l'exécution, grâce au type réel de l'objet, qu'un pointeur ou une référence sur une classe de base désigne bien un T. Exige une classe polymorphe (au moins une fonction virtuelle). Échec : un pointeur donne NULL, une référence lève std::bad_cast.dynamic_cast<B *>(basePtr)
const_cast<T>(x)Ajoute ou retire const (ou volatile), rien d'autre : const_cast<long *> d'un const int * est refusé. Écrire dans un objet défini const reste un comportement indéfini, selon la norme.Aucun exercice du module n'en a besoin

Pourquoi ne pas rester au cast C ? Parce qu'il essaie tout : static_cast, puis reinterpret_cast, et il peut même retirer un const, sans rien dire et sans nom à chercher. Constaté avec clang et -Wall -Wextra -Werror : (Data *)raw (un entier lu comme pointeur) et (char *)ptrConst compilent sans un avertissement, et (A *)p sur un objet qui est en réalité un B renvoie un pointeur non nul, sans aucun contrôle.

Voici le choix classique pour ce module. Le sujet ne l'impose pas : c'est la réponse que tu dois pouvoir argumenter.

04

ex00 · ScalarConverter

Ta classe reçoit une chaîne qui représente un littéral C++ dans sa forme la plus courante (p. 9), devine de quel type il s'agit, puis affiche sa valeur sous les quatre types scalaires. Elle ne stocke rien : une seule méthode statique, pas d'objet.

Fichiers à rendre (p. 9) : Makefile, ScalarConverter.hpp, ScalarConverter.cpp et ton programme de test main.cpp (voir la note sur les noms, section précédente). Le sujet ne fixe pas le type du paramètre de convert : une const std::string & est un choix simple.

ScalarConverter.hpp
#ifndef SCALARCONVERTER_HPP
# define SCALARCONVERTER_HPP

# include <string>

class ScalarConverter
{
	public:
		static void	convert(const std::string &literal);

	private:
		ScalarConverter();                                    // les quatre membres canoniques sont privés :
		ScalarConverter(const ScalarConverter &other);        // personne ne peut créer, copier
		ScalarConverter &operator=(const ScalarConverter &other); // ni détruire un ScalarConverter
		~ScalarConverter();
};

#endif

Le travail se fait en trois temps. Le sujet les décrit ainsi (p. 11) : détecter le type du littéral, le convertir depuis la chaîne vers son vrai type, puis le convertir explicitement vers les trois autres et afficher.

1. Détecter le type. Le sujet donne des exemples ; la façon de reconnaître chaque forme est à toi (ce tableau est un conseil). Fais les pseudo-littéraux en premier.

float0.0f, -4.2f, 4.2f (p. 9)Un signe facultatif, des chiffres, un seul point, des chiffres, puis f.
double0.0, -4.2, 4.2 (p. 10)Comme le float, sans le f.

Sauf pour les char, seule la notation décimale est utilisée (p. 9) : ni exposant (1e3), ni hexadécimal (0x10). Et les caractères non affichables ne seront pas donnés en entrée (p. 9). Tout le reste est une entrée invalide : à toi de décider ce que tu affiches, mais jamais de planter.

2. Convertir. Pour passer de la chaîne à un nombre, le sujet autorise « toute fonction » qui convertit une chaîne en int, float ou double (p. 9), comme strtod. Ce n'est pas un cast : c'est de l'analyse de texte, et c'est elle qui est piégeuse (voir les pièges). Ensuite, passer d'un type numérique à un autre est là où le cast intervient : static_cast. Mais un cast ne dit pas « impossible » : c'est à toi de tester la plage avant de caster. Le sujet demande un message quand la conversion n'a pas de sens ou déborde, et de penser aux en-têtes pour les limites numériques et les valeurs spéciales (p. 11).

Les décimales, c'est toi qui les imposes. Constaté avec clang en C++98 : std::cout << 42.0f affiche 42 (pas 42.0), 0.0f affiche 0, et 2147483648.0f affiche 2.14748e+09. Avec std::fixed et std::setprecision(1) (<iomanip>), on obtient bien 42.0, 0.0 et 2147483648.0, mais 3.14159 devient 3.1 et 4.25f devient 4.2 : on perd des chiffres. Le sujet ne fixe que ses exemples ; la démo ci-dessous garde le moins de décimales qui redonnent la même valeur, au moins une. ex01 · Serializer

Un pointeur, c'est une adresse, donc un nombre. uintptr_t est un type d'entier non signé assez grand pour en contenir un. Ta classe a deux méthodes statiques : serialize lit l'adresse comme un entier, deserialize relit cet entier comme une adresse. Rien n'est copié : l'objet Data reste où il est.

Fichiers à rendre (p. 12) : Makefile, Serializer.hpp, Serializer.cpp, Data.hpp (et Data.cpp si tu en as besoin) et main.cpp. Le sujet rappelle de ne pas oublier les fichiers de Data.

Serializer.hpp
#ifndef SERIALIZER_HPP
# define SERIALIZER_HPP

# include <stdint.h>
# include "Data.hpp"

class Serializer
{
	public:
		static uintptr_t	serialize(Data *ptr);
		static Data			*deserialize(uintptr_t raw);

	private:
		Serializer();
		Serializer(const Serializer &other);
		Serializer &operator=(const Serializer &other);
		~Serializer();
};

#endif
Data.hpp
#ifndef DATA_HPP
# define DATA_HPP

# include <string>

struct Data
{
	std::string	name;
	int			value;
};

#endif

Le cast. Le choix classique est reinterpret_cast dans les deux sens : tu ne convertis pas une valeur, tu relis une adresse. static_cast est refusé pour ça, comme on l'a vu dans la section précédente. Pour uintptr_t, inclus <stdint.h> : il compile avec -std=c++98. <cstdint> est du C++11 ; clang sous macOS l'accepte aussi en mode C++98 (constaté), mais à vérifier avec le compilateur de ton école.

Le test (p. 12). Crée un Data avec des attributs, passe son adresse à serialize, donne le résultat à deserialize, puis vérifie que le pointeur obtenu est égal à l'original, avec == sur les deux Data *. Affiche aussi l'entier en décimal et en hexadécimal : c'est parlant en défense.

🎲

Une vraie adresse n'est jamais la même. Constaté sur macOS : deux exécutions du même programme affichent deux adresses de pile différentes (0x16d216558 puis 0x16b2e2558). Ne cherche donc pas à comparer ton affichage à une valeur fixe. Sur cette machine, sizeof(uintptr_t) et sizeof(void *) valent 8, sizeof(unsigned int) vaut 4 : ranger une adresse dans un unsigned int est refusé (voir le tableau précédent).

La démo utilise une adresse simulée, pour avoir toujours les mêmes chiffres. Appuie sur serialize(ptr), puis deserialize(raw) : le pointeur est le même. Ajoute 1 à l'entier : le pointeur change, et le verdict devient faux.

Démo : un objet Data fictif à l'adresse simulée 0x7ffee3b2a1c0. serialize(ptr) renvoie l'entier 140732718555584 (en hexadécimal 0x7ffee3b2a1c0) ; deserialize(raw) rend la même adresse, donc ptr == deserialize(serialize(ptr)) est vrai. Avec l'entier plus 1, soit 140732718555585, on obtient 0x7ffee3b2a1c1 : un autre pointeur, que l'on ne doit jamais déréférencer.

ex02 · Identify real type

Tu as un pointeur (ou une référence) sur Base, mais l'objet peut être un A, un B ou un C. Comment savoir lequel, sans typeid ? En demandant à dynamic_cast : il compare le vrai type de l'objet à celui que tu proposes, et te dit oui ou non à l'exécution.

Fichiers à rendre (p. 13) : Makefile, Base.hpp et Base.cpp, A.hpp, B.hpp, C.hpp, un fichier pour generate et identify (à toi de le nommer), et main.cpp. Pourquoi un Base.cpp ? Parce qu'un corps de fonction dans un header, même un simple {} après le destructeur, est une implémentation de fonction dans un header : le sujet met 0 (p. 4). Ne prends pas ce risque.

Base.hpp
#ifndef BASE_HPP
# define BASE_HPP

class Base
{
	public:
		virtual ~Base();   // le seul membre : public et virtuel (p. 13)
};

#endif
A.hpp
#ifndef A_HPP
# define A_HPP

# include "Base.hpp"

class A : public Base {};   // vide : B et C sont identiques

#endif

Pourquoi le destructeur virtuel ? Parce que dynamic_cast n'accepte que du polymorphe : une classe avec au moins une fonction virtuelle. Sans virtual, le compilateur répond « 'Base' is not polymorphic » (constaté). Et détruire un A à travers un Base * sans destructeur virtuel est un comportement indéfini.

generate. Elle crée au hasard un A, un B ou un C avec new et le rend comme Base * ; le sujet te laisse libre du tirage au sort (p. 13). Qui fait le delete ? Celui qui a appelé generate. Initialise le générateur une seule fois, dans main (voir les pièges).

identify(Base *p). Essaie un dynamic_cast vers chaque type : un pointeur qui n'est pas du bon type donne NULL, le premier résultat non nul te donne la réponse.

identify(Base &p). Même idée, mais le sujet interdit les pointeurs dans cette fonction (p. 13). Une référence ne peut pas valoir « rien » : un dynamic_cast vers une référence qui échoue ne renvoie pas NULL, il lève une exception (std::bad_cast, dont what() donne std::bad_cast ici). Tu as donc besoin d'un try / catch. Le piège : std::bad_cast est déclarée dans <typeinfo>, l'en-tête que le sujet t'interdit d'inclure (p. 13). Attrape plutôt std::exception, qui vient de <exception> : constaté, ça compile et ça marche sans jamais inclure <typeinfo>.

Ce que fait la démo : une chaîne d'essais, A d'abord, puis B, puis C, arrêtée au premier succès. Pour un objet de type A, un seul essai suffit ; pour un C, deux échecs précèdent le succès.

Démo : un objet dont le type réel est caché. Pour un objet de type B : version pointeur, dynamic_cast<A *> renvoie NULL, dynamic_cast<B *> renvoie un pointeur valide et la fonction affiche B ; version référence, dynamic_cast<A &> lève std::bad_cast, dynamic_cast<B &> réussit et la fonction affiche B. Pour A, le premier essai réussit ; pour C, les deux premiers échouent.

❓

Et un Base tout nu ? generate ne le produit jamais, et le sujet ne demande que A, B ou C (p. 13). Mais rien ne t'empêche d'appeler identify sur un new Base : constaté, les trois essais échouent. Prévois ce que tes fonctions font dans ce cas (un message, ou rien), pour ne jamais être surpris en défense.

08

Pièges classiques

⚠️

nanf ou nan ? Les six pseudo-littéraux sont des chaînes exactes (p. 9-10), à reconnaître avant tout le reste. À l'affichage, std::cout écrit nan, inf et -inf (constaté) : le f de la ligne float et le + sont à toi. Pour fabriquer ces valeurs, <limits> fournit quiet_NaN() et infinity() dans std::numeric_limits<double>.

⚠️

-0.0. Le zéro négatif existe. Avec std::fixed et std::setprecision(1), -0.0 s'affiche -0.0 (constaté) ; sans fixed, -0. Le sujet ne le teste pas : décide du résultat de tes quatre lignes (ici : Non displayable, 0, -0.0f, -0.0) et reste cohérent.

⚠️

42f n'est pas 42.0f. Un float s'écrit avec un point. En C++, float f = 42f; ne compile même pas (clang : « invalid digit 'f' in decimal constant »). Ton détecteur doit refuser 42f.

⚠️

Une apostrophe mal fermée. 'a, 'ab' et '' ne sont pas des char : refuse-les. Et le shell mange les apostrophes (voir la section ex00) : décide ce que ton programme fait d'un caractère seul comme c.

⚠️

strtod accepte beaucoup plus que le sujet. Constaté : strtod("42abc") renvoie 42 et seul endptr pointe vers abc ; une espace de tête est acceptée ; "0x10" donne 16, "1e3" donne 1000 ; "inf", "infinity" et "NaN" passent aussi. Valide donc la forme de la chaîne avant, et vérifie endptr. atoi("abc") renvoie 0, comme atoi("0") : impossible de distinguer l'erreur. Enfin std::stod, std::stof et std::stoi sont du C++11, interdit (p. 3) : le clang de macOS les compile pourtant avec -std=c++98 (constaté), donc ne te fie pas à ton compilateur local ; à vérifier avec celui de ton école.

⚠️

Un int hors plage. Convertir un double dont la valeur tronquée ne tient pas dans un int est un comportement indéfini selon la norme. Le résultat n'est pas garanti : static_cast<int>(3e10) peut donner 2147483647, une autre valeur, ou changer selon la machine, le compilateur et l'optimisation. Teste la plage avant de caster, avec les bornes de <climits> ou de <limits>. Même logique pour char : static_cast<char>(321) donne 'A' (constaté), sans prévenir.

⚠️

Les caractères non affichables. Les codes 0 à 31 et 127 donnent Non displayable. std::isprint (<cctype>) accepte les codes de 32 à 126, soit 95 caractères (constaté, locale « C »), mais attend une valeur entre 0 et 255 : ne lui passe pas un char négatif. Pour 128 à 255, char est signé ici (CHAR_MIN vaut -128) et static_cast<char>(200) vaut -56 : le sujet ne tranche pas, ce cours affiche impossible.

⚠️

« Non instanciable » = les quatre membres privés. Un constructeur par défaut privé suffit à empêcher ScalarConverter s;, mais l'OCF demande aussi le constructeur de copie, l'opérateur d'affectation et le destructeur : déclare-les tous les quatre privés. Constaté : le compilateur répond « calling a private constructor of class 'ScalarConverter' » puis « variable of type 'ScalarConverter' has private destructor ». Même chose pour Serializer.

⚠️

Le mauvais cast en défense. reinterpret_cast pour passer d'un float à un int : refusé, il ne convertit pas les valeurs. static_cast pour un pointeur vers un entier : refusé. Un cast C partout : ça compile, mais tu n'as pas choisi. Prépare une phrase par exercice, comme à l'étape 1.

⚠️

Comparer les pointeurs, pas les contenus. Le test d'ex01 demande que le pointeur retrouvé soit égal à l'original (p. 12) : == sur deux Data *, pas une comparaison des champs. Si tu stockes l'adresse dans un type trop petit (unsigned int), le compilateur refuse ; uintptr_t vient de <stdint.h>. Et n'écris jamais une adresse en dur dans ton test : elle change à chaque exécution.

⚠️

identify(Base &) sans pointeur ni typeinfo. Ne prends pas l'adresse de la référence : le sujet l'interdit (p. 13). Un dynamic_cast sur une référence qui échoue lève une exception : il te faut un try / catch. N'écris pas typeid : clang répond « you need to include <typeinfo> before using the 'typeid' operator » (constaté), et le sujet l'interdit. Pour attraper l'exception sans <typeinfo>, utilise std::exception (<exception>). Avec libc++ (clang, macOS), même catch (const std::bad_cast &) compile avec seulement <exception> (constaté) : ne compte pas dessus ailleurs.

⚠️

Le virtual oublié sur ~Base. Sans fonction virtuelle, dynamic_cast ne compile plus (« 'Base' is not polymorphic »), et supprimer un objet dérivé via un Base * devient un comportement indéfini. N'écris pas non plus le corps du destructeur dans le header (p. 4).

⚠️

srand dans generate. Si tu initialises le générateur à chaque appel avec time(NULL), tous les objets créés pendant la même seconde sont du même type : constaté, douze appels de suite ont tous donné le même type (C). Appelle srand une seule fois, dans main.

Comment je l'ai fait

J'ai gardé les trois exercices simples. Pour ScalarConverter, les quatre membres canoniques sont privés. Une fonction détecte le type du littéral à la main, pseudo-littéraux d'abord, puis char, int, float et double. La valeur passe ensuite une seule fois par un double, et chaque ligne de sortie teste sa plage avant d'utiliser static_cast. Je mets une seule décimale quand le nombre est entier, sinon la précision par défaut. Serializer n'a que deux méthodes statiques en reinterpret_cast, essayées sur un Data de la pile puis du tas. Pour l'exercice 02, la version pointeur enchaîne les dynamic_cast et regarde s'ils renvoient NULL, tandis que la version référence les essaie dans des blocs try qui attrapent std::exception, sans jamais inclure <typeinfo>. J'ai aussi testé avec un Base nu.
