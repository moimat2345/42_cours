The CPP04 module

Why a pointer to Animal makes a Dog bark, what virtual changes, why a copy must be deep, and what an abstract class is for.

subject: CPP Module 04 · version 13.1 · C++98 · c++ -Wall -Wextra -Werror -std=c++98

01

The module in brief

CPP04 takes you from “classes that inherit” to “classes you use without knowing exactly which one you are holding”. You write a small family of Animal, Dog and Cat. When you call makeSound() on a pointer to Animal, the sound of the animal actually pointed to must come out (ex00).

Then every dog and cat gets a Brain allocated with new (ex01): you need deep copies and correct destructors. ex02 makes Animal abstract. ex03, which is optional, is where you write “interfaces”: AMateria, ICharacter, IMateriaSource.

🧭

Three questions for the whole module. Which function is called: the one for the pointer type, or the one for the object type? Who destroys what, and in which order? When I copy, do I copy the object, or only the address of what it owns?

03

Polymorphism in practice

An Animal* can hold the address of a Dog: a dog is an animal. This is the subtype polymorphism the subject's title talks about. But then two types are involved:

🏷️

The pointer type

  • →The one you write in the declaration: Animal*.
  • →The compiler knows it, and it never changes.
🐕

The object type

  • →The type of the object really created: new Dog().
  • →It is only known at run time.
the idea
Animal* a = new Dog();   // pointer type: Animal*   |   object type: Dog
a->makeSound();          // Animal's version, or Dog's?

Without virtual, the compiler only looks at the pointer type and picks the function at compile time (static binding): it will be Animal::makeSound. With virtual in the base class, the choice is postponed to run time (dynamic binding): the real type of the object decides, so Dog::makeSound.

DeclarationmakeSound virtual?Function calledWho decides
Animal* a = new Dog();yesDog::makeSoundthe object, at run time
Animal* a = new Dog();noAnimal::makeSoundthe pointer, at compile time
Dog* d = new Dog();doesn't matterDog::makeSoundthe pointer: it is already a Dog*
WrongAnimal* w = new WrongCat();no (that is the point of WrongAnimal)WrongAnimal::makeSoundthe pointer, at compile time
WrongCat* c = new WrongCat();noWrongCat::makeSoundthe pointer: it is a WrongCat*

How does it work? The C++ standard says what a virtual call must do, not how. But the mainstream compilers all do the same thing: every class that has a virtual function gets a virtual table (vtable), an array of pointers to its virtual functions, and every object of that class holds a hidden pointer (the vptr) to its class's table. A virtual call reads the object's vptr, takes the function's slot in the table, and jumps to the address found. A hint: observed with clang on macOS (arm64), an empty class takes 1 byte, and the same class with a virtual destructor takes 8, the size of a pointer.

Play with the demo: change the pointer type, the object type and the virtual switch. The two cases from the subject are in the buttons.

Demo: a pointer of one type, an object of another type, and a virtual switch on makeSound. With Animal* a = new Dog(); and virtual, the call a->makeSound() goes through the virtual table of Dog and prints Woof. With WrongAnimal* w = new WrongCat(); without virtual, the call is bound at compile time to WrongAnimal::makeSound and prints WrongAnimal sound: the WrongCat is ignored.

⚠️

Overriding means the same signature. C++98 has no override keyword. If Dog::makeSound() does not have the same const as Animal::makeSound() const, you override nothing: you create another function that hides the first one, and the call through an Animal* still prints Animal's sound. Observed with Apple clang on macOS: -Wall -Wextra -Werror rejects this code (-Woverloaded-virtual). To check with your school's compiler. Repeating virtual in the derived classes is optional but makes the intent readable.

The virtual destructor. When you write delete a; with a of type Animal*, the same choice comes up: which destructor to call? Without virtual on ~Animal(), the compiler calls the one for the pointer type, and only that one. Dog's destructor does not run, so whatever it freed (the ex01 Brain) is lost: that is a leak, and under the C++ standard it is even undefined behavior. The rule to remember: as soon as a class is used as a base and its objects are destroyed through a base pointer, its destructor is virtual.

With a virtual destructor, delete a; destroys the Dog part first (which frees its Brain), then the Animal part. Construction goes the other way around: Animal first, then Dog. This is what the subject calls the destructors being called in the expected order (p. 10).

⚠️

Polymorphism goes through a pointer or a reference. If you pass a Dog to a function that takes an Animal by value, the object is copied into an Animal: the Dog part is lost (this is called slicing) and makeSound() prints Animal's sound. Observed with clang on macOS; with a reference (const Animal&), the dog's sound comes out.

ex00 · Polymorphism

The subject describes a base class Animal with one protected attribute std::string type; (p. 8). Dog and Cat inherit from it and set their type to "Dog" and "Cat"; Animal's can stay empty or hold whatever you like (p. 8). Every animal can do makeSound(). To check you understood, you add WrongAnimal and WrongCat: if you replace Animal and Cat with the “wrong” ones in the subject's main, the WrongCat must print the WrongAnimal sound (p. 9).

Files to turn in (p. 8): Makefile, main.cpp, *.cpp, *.{h, hpp}. For you, that means Animal, Dog, Cat, WrongAnimal, WrongCat, each with its own .hpp and .cpp.

Animal's header (declarations only; the canonical form is required since module 02):

ex00/Animal.hpp
#ifndef ANIMAL_HPP
#define ANIMAL_HPP

#include <string>

class Animal
{
    protected:
        std::string     type;                   // required: protected attribute (p. 8)

    public:
        Animal();
        Animal(const Animal& other);
        Animal& operator=(const Animal& other);
        virtual ~Animal();                  // virtual: see "polymorphism"

        virtual void    makeSound() const;   // virtual AND const
        std::string     getType() const;
};

#endif

getType() and makeSound() are names the subject's main uses (p. 9). That main handles const Animal*: both functions must therefore be const, otherwise the compiler rejects the call. Dog and Cat look alike:

ex00/Dog.hpp
#include "Animal.hpp"

class Dog : public Animal
{
    public:
        Dog();                                  // sets type to "Dog", prints its message
        Dog(const Dog& other);
        Dog& operator=(const Dog& other);
        virtual ~Dog();

        virtual void makeSound() const;     // same signature as Animal's
};

WrongAnimal is a copy of Animal with a single difference: makeSound() is not virtual there. Still give it a virtual destructor: the exercise is about makeSound, not about a faulty destruction. WrongCat inherits from WrongAnimal and overrides makeSound() like Cat does. Without virtual, that override is never chosen through a WrongAnimal*: this is exactly what the exercise wants you to observe.

The expected result. The constructor and destructor messages are free (one message per class). For the rest, with the subject's main, you should see this (the sounds are examples):

./a.out | cat -e (without the construction messages)

Cat $
Meow$
Woof$
Animal sound$

The $ marks the end of each line (cat -e). The first two lines are the getType() of j and then of i: the space before the $ comes from the << " " that the subject's main writes (p. 9). The three sounds follow the order of the calls (i, j, meta). With the “wrong” classes, makeSound() on a const WrongAnimal* that points to a WrongCat must print the WrongAnimal sound.

ex01 · Brain and the deep copy

The subject (p. 10) asks for a Brain class that holds an array of 100 std::string called ideas. Dog and Cat each get a private Brain* attribute: they create their brain with new Brain() on construction and delete it on destruction. In your main, you create and fill an array of animals, half Dog, half Cat, then loop over it at the end to delete every animal directly as an Animal. Finally, a copy of a Dog or a Cat must not be shallow, and you have to test that.

Files to turn in (p. 10): the ones from the previous exercise + *.cpp, *.{h, hpp}. So you add Brain.hpp and Brain.cpp, and Dog and Cat change.

ex01/Brain.hpp
#include <string>

class Brain
{
    private:
        std::string     ideas[100];        // required: 100 std::string, called ideas (p. 10)

    public:
        Brain();
        Brain(const Brain& other);
        Brain& operator=(const Brain& other);
        ~Brain();

        // a way to read and write an idea: free names, the subject gives none
};
ex01/Dog.hpp (Cat is the same)
class Dog : public Animal
{
    private:
        Brain*  brain;                         // required: private Brain* attribute (p. 10)

    public:
        Dog();                                 // new Brain()
        Dog(const Dog& other);                  // DEEP copy
        Dog& operator=(const Dog& other);       // DEEP copy
        virtual ~Dog();                         // delete brain

        virtual void makeSound() const;
};

Shallow or deep? If you do not define a copy constructor, the compiler writes one that copies each attribute as is. For a Brain*, it copies the address, not the brain: the two dogs then share the same Brain. Observed with clang on macOS: changing ideas[0] through the copy also changes the original, then destroying both dogs does two deletes on the same address; the second ~Brain() runs once more, then the program is killed (exit status 133). A deep copy allocates a new Brain and copies the contents into it. Try both in the demo.

Demo: an “original” Dog owns a Brain whose ideas[0] is food. With a shallow copy, Dog copy(original); only copies the pointer: both dogs share the same Brain, changing the copy's ideas[0] also changes the original, and destroying both frees the same Brain twice (double delete, undefined behavior). With a deep copy, the copy gets its own Brain: changing the copy does not touch the original, and each Brain is freed once.

What a deep copy must do in Dog and Cat (the code is up to you):

📋

Copy constructor

  • →Calls Animal's copy constructor in the initialization list (: Animal(other)). Otherwise Animal's default constructor runs and the type is not copied (observed with clang: no warning).
  • →Allocates a new Brain built from the other's: new Brain(*other.brain).
🟰

operator=

  • →Guards against self-assignment (this != &other), see the pitfalls.
  • →Copies the Animal part, then either copies the contents into the existing Brain, or frees the old one and allocates a new one.
  • →Either way, never a shared pointer. Returns *this.

The array of animals. To delete each element “directly as an Animal” (p. 10), the array holds Animal* pointers. An array of Animal by value cannot hold anything more than an Animal (the dogs would be truncated). The idea fits in a few lines:

main.cpp (the idea)
Animal* animals[4];                       // POINTERS; pick an even number for "half and half"
// ... half of the slots get new Dog(), the other half new Cat() ...
for (int i = 0; i < 4; i++)
    delete animals[i];                   // one delete per element, through an Animal*
🔎

Check for leaks. The subject insists: “Don't forget to check for memory leaks” (p. 10). On macOS: leaks --atExit -- ./your_program (tested here). On Linux: valgrind --leak-check=full ./your_program (not tested here). For the deep copy, the minimal test: change ideas[0] of the copy, print the original, check it did not move, then do the same test for operator=.

expected order for a Dog destroyed through an Animal*
Animal constructor called   ← example messages: yours will differ
Brain constructor called
Dog constructor called
...
Dog destructor called       ← the most derived class first
Animal destructor called    ← then the base (the Brain was freed in ~Dog)

ex02 · Abstract class

The subject (p. 12) points out that a plain Animal makes no sense: it makes no sound. It asks you to fix the class so that nobody can instantiate it, and says everything must work as before. If you want, you can rename the class with an A prefix (AAnimal). Files to turn in: the ones from the previous exercise + *.cpp, *.{h, hpp}.

In C++, a class is abstract as soon as it has at least one pure virtual function: you declare it with = 0 instead of giving it a body. The change fits in one line of the header:

ex02/Animal.hpp (the change)
        virtual void    makeSound() const = 0;   // pure: Animal becomes abstract
🚫

What no longer compiles

  • →new Animal() and Animal a;: remove them from the ex00 main.
  • →A derived class that forgets to override makeSound becomes abstract in turn.
✅

What still works

  • →Pointers and references Animal* / Animal&.
  • →Animal's constructor and destructor: Dog and Cat call them. WrongAnimal stays instantiable: the subject only talks about Animal.
what the compiler says (Apple clang, macOS)
error: allocating an object of abstract class type 'Animal'
note: unimplemented pure virtual method 'makeSound' in 'Animal'

The exact text varies from one compiler to another. If you rename it to AAnimal, the files become AAnimal.hpp and AAnimal.cpp (a class file carries the name of the class, p. 3), and Dog and Cat inherit from AAnimal. Your test main keeps the same scenarios, except for the lines that instantiate the class: keep them commented out to show during the defense that the compiler rejects them.

ex03 · Interfaces (optional)

📌

Status. “You can pass this module without doing exercise 03” (p. 16). Do ex00 to ex02 perfectly first.

The subject reminds you that C++ has no “interface” in the strict sense, but that a pure abstract class is commonly called one (p. 13), that is, a class with no attributes and no code, only pure virtual functions. Here: ICharacter and IMateriaSource, whose complete definitions the subject gives (p. 14 and 15). You write the concrete classes. Files to turn in (p. 13): Makefile, main.cpp, *.cpp, *.{h, hpp}.

ClassWhat the subject says
AMateriaAbstract class: AMateria(std::string const & type), getType(), a pure virtual clone(), a virtual use(ICharacter&) (p. 13). Copying the type when assigning one Materia to another “doesn't make sense” (p. 14).
Ice, CureTypes "ice" and "cure" in lowercase. clone() returns a new instance of the same type. use prints * shoots an ice bolt at <name> * and * heals <name>'s wounds *, without the angle brackets (p. 14).

Full inventory, or use / unequip on a non-existent slot: nothing happens, but no bugs. unequip must not delete (p. 14). A constructor taking the name. Every copy is deep, and the Materias are deleted before being replaced, and on destruction (p. 15).

The expected result. The subject provides a main (p. 16): a source that learns Ice and Cure, a character me that creates and equips both Materias, then uses them on bob. The output must be, with | cat -e:

./a.out | cat -e
* shoots an ice bolt at bob *$
* heals bob's wounds *$
⚠️

Who owns the Materia passed to learnMateria? The subject's main does src->learnMateria(new Ice()). If your function clones the Materia, keeps the clone and forgets the original, that Ice is never freed. Observed with leaks on macOS: 2 leaks with exactly the subject's main. The subject says learnMateria “copies” the Materia (p. 15), so clone-then-delete-the-original is the reading that follows the subject. Keeping the pointer you received (the source becomes its owner) also gives 0 leaks (tested), but departs from the word “copies”: check it with your evaluator. Pick one, apply the rule also when all 4 slots are full, and be able to explain it.

⚠️

Headers that include each other in a loop. AMateria mentions ICharacter in use, and ICharacter mentions AMateria in equip. If each includes the other, it does not compile. Put a forward declaration (class ICharacter;) in the header, and include the real header in the .cpp that calls getName(). Each header must remain usable on its own (p. 4): compile them one by one to check.

⚠️

The subject's {}. The subject's interfaces write virtual ~ICharacter() {} with an empty body in the header (p. 14 and 15), while the general rule forbids any function implemented in a header (p. 4). The subject does not say how to reconcile the two: to check with your evaluator. A safe option is to declare the destructor in the header and define it in a .cpp.

09

Classic pitfalls

⚠️

A non-virtual base destructor. Animal* a = new Dog(); delete a; only calls ~Animal(): the dog's Brain is never freed. Observed on macOS with leaks: 1 leak. With Apple clang and the subject's flags, this code does not even compile (-Wdelete-non-abstract-non-virtual-dtor); that is not guaranteed with another compiler, do not count on it. Put virtual on Animal's destructor (and WrongAnimal's).

⚠️

A forgotten const on makeSound. Two cases, observed with Apple clang. If Animal::makeSound is not const, the call on the subject's const Animal* does not compile. If only Dog::makeSound is not const, the function overrides nothing: -Wall -Wextra -Werror rejects it, but without -Werror the program runs and prints Animal's sound.

⚠️

Shallow copy of the Brain*. No copy constructor, or a copy constructor that does brain = other.brain: both animals share a brain, and the second delete is a double delete (see the demo). The same trap exists in operator=: do not write this->brain = other.brain.

⚠️

Self-assignment in operator=. If you do delete brain; then brain = new Brain(*other.brain); without asking whether other is *this, you read a brain you just freed. Observed on macOS: the idea "food" vanished (empty string) or, with MallocScribble=1, the program crashed. Test with a reference (Dog& r = a; a = r;): a a = a; written as is gets rejected by clang with -Werror (-Wself-assign-overloaded). Guard with if (this != &other).

⚠️

Instantiating the abstract class. new Animal(), Animal a; or an array of Animal by value no longer compile after ex02. The same goes for a derived class that forgets to override makeSound: it is abstract in turn.

⚠️

The array of Animal* to fill and then destroy. The array holds pointers, not Animals. To fill it, write an if / else: cond ? new Dog() : new Cat() does not compile in C++98 (“incompatible operand types”, observed with clang). To destroy it, one delete on each slot, not a single delete on the array. If you allocated the pointer array itself (new Animal*[n]), it also needs its own delete[] (forgotten, leaks reports 1 leak on macOS). Pick an even number so that “half and half” makes sense, and check for leaks.

⚠️

One message for all the classes. The subject asks for a specific message per class (p. 8): otherwise the construction and destruction trace proves nothing anymore. Reusing the same text and changing the class name is enough.

⚠️

ex03: an unequip that deletes, or that loses the pointer. The subject forbids the delete in unequip (p. 14). But if you simply set the slot to 0 without keeping the address, the Materia is lost: a leak. Keep the address somewhere (on the floor, in the character, or in your main) and free it at the end.

How I did it

I went exercise by exercise, starting each one from the previous folder. From ex00, Animal has a virtual destructor and a virtual const makeSound; WrongAnimal is its twin without virtual on makeSound. Every class prints its own message in its constructors, its assignment operator and its destructor. Brain copies its hundred ideas in a loop. 📌 Key takeaways (evaluation defense)

  • ✓
    Who decides which function is called? Without virtual, the pointer type, at compile time. With virtual, the real type of the object, at run time.
  • ✓
    How does it work? One virtual table per class and a hidden pointer in every object. The standard does not mandate this mechanism, but the mainstream compilers use it.
  • ✓
    Why a virtual destructor? So that delete on an Animal* first calls Dog's destructor (which frees its Brain), then Animal's.
  • ✓
    What is WrongAnimal for? To show what happens when makeSound is not virtual: the WrongCat's sound is never used through a WrongAnimal*.
  • ✓
    Shallow or deep copy? Shallow: the Brain's address is copied, both animals share it, and the delete happens twice. Deep: a new Brain with the same contents.
  • ✓
    What does your operator= do? It guards against self-assignment, copies the Animal part, never shares a pointer, and returns *this.
  • ✓
    Abstract class. At least one pure virtual function (= 0). You cannot instantiate it, but you use it through a pointer or a reference. Its derived classes must override the pure function.
  • ✓
    The array of animals. Animal*s, half Dog half Cat, one delete per slot, zero leaks.
  • ✓
    Interface in C++98. No keyword: a pure abstract class. ICharacter and IMateriaSource only have pure virtual functions and a virtual destructor. ex03 is optional (p. 16).
  • ✓
    General rules. c++ -Wall -Wextra -Werror -std=c++98, canonical form, no using namespace or friend, no STL, no function in a header, include guards, one message of its own per class.
