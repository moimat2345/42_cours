C++ · Module 07 · Templates

Du code générique

Écrire une seule fois une fonction ou une classe qui marche pour tous les types : swap, min, max, iter, puis un Array<T>. Ce que le sujet demande, et les pièges que le compilateur te réserve.

sujet : en.subject (1).pdf · version 10.1 · c++ -Wall -Wextra -Werror -std=c++98

01

Le module en bref

Le module 07 introduit les templates. Au lieu d'écrire un swap pour les int, un autre pour les std::string, un autre pour tes propres classes, tu écris un seul modèle : le compilateur fabrique la version qu'il faut pour chaque type utilisé.

Trois exercices, de plus en plus riches. ex00 : trois petites fonctions, swap, min et max. ex01 : une fonction iter qui appelle une fonction sur chaque élément d'un tableau, que ce tableau soit const ou non. ex02 : une classe Array<T>, un tableau dynamique avec copie profonde et accès contrôlé par operator[].

Il y a peu de code à écrire, mais beaucoup de détails de compilation : où ranger le code, quel type le compilateur déduit, ce qui est const. C'est là que ce cours t'aide.

📖

Les numéros de page entre parenthèses, comme (p. 8), sont ceux imprimés en bas des pages du sujet (version 10.1) : la page du PDF porte un numéro de plus. Garde le PDF ouvert à côté : ce cours explique le sujet, il ne le remplace pas. Les messages de compilateur cités viennent d'Apple clang 17 sous macOS (c++ -std=c++98 -Wall -Wextra -Werror) ; g++ sur ta machine d'école peut les formuler autrement : à vérifier.

Le sujet consacre un chapitre aux IA (p. 6-7) : raisonner d'abord, ne pas demander de réponses toutes faites. Ce cours explique les notions et les pièges ; le code de tes fichiers, c'est à toi de l'écrire.

03

Les templates, sans mystère

Un modèle, pas une fonction

Un template de fonction n'est pas une fonction : c'est un modèle. Le compilateur n'en tire du code que lorsqu'on l'appelle avec un type précis. Voici un exemple inventé, sans rapport avec le sujet :

twice.cpp · un modèle d'exemple
template <typename T>
T twice(T x)
{
	return x + x;
}

int main()
{
	std::cout << twice(21) << std::endl;    // T = int
	std::cout << twice(1.5) << std::endl;   // T = double
	return 0;
}

Le compilateur déduit T en regardant l'argument : 21 est un int, 1.5 un double. Ici, il fabrique deux fonctions distinctes. On le voit dans le fichier objet (constaté avec clang sur macOS) :

terminal · adresses retirées
$ c++ -std=c++98 -c twice.cpp -o twice.o
$ nm -C twice.o | grep twice
T double twice<double>(double)
T int twice<int>(int)

Une version par type utilisé, et seulement celles-là. Deux conséquences : le compilateur doit voir le corps du template au moment de l'appel, et une erreur dans le corps n'apparaît que lorsqu'une version est fabriquée. Un template jamais appelé n'est vérifié qu'à moitié : teste-le avec plusieurs types.

Pourquoi tout va dans le .hpp

Essaie de ranger le corps dans un .cpp, comme pour une fonction ordinaire : le .hpp ne contient que la déclaration, le .cpp le corps. Chaque fichier compile sans erreur. Mais main.cpp demande swap<int> et ne voit que la déclaration ; le .cpp, lui, a le corps mais personne n'y demande swap<int>, donc il ne fabrique rien. Il reste un appel vers une fonction qui n'existe nulle part :

terminal · erreur de lien (macOS)
Undefined symbols for architecture arm64:
  "void swap<int>(int&, int&)", referenced from:
      _main in wmain.o
ld: symbol(s) not found for architecture arm64

C'est pour cela que le sujet exige que les templates soient définis dans les en-têtes (p. 8). Sous Linux, le message de l'éditeur de liens est formulé autrement (« undefined reference to »).

typename ou class ?

Dans template <typename T>, on peut écrire class à la place de typename : c'est équivalent ici (les deux versions compilent). Choisis-en un et garde-le dans tout le module.

Le :: des appels du sujet

Dans le main du sujet (p. 9), tout est écrit ::swap(a, b), ::min(a, b). Un :: devant un nom veut dire « cherche dans l'espace global, et nulle part ailleurs » : c'est donc ton swap, pas celui de std. Sans lui, la recherche peut trouver aussi la version de la bibliothèque standard, et le compilateur refuse de choisir. Vérifié avec clang et libc++, sans using namespace :

terminal · min(c, d) sur deux std::string, sans ::
error: call to 'min' is ambiguous
note: candidate function [with _Tp = std::string]
note: candidate function [with T = std::string]

Le compilateur cherche aussi dans l'espace de noms des arguments (std, pour une std::string) : il trouve std::min en plus du tien. Avec using namespace std; (interdit dans ce module, p. 4), même un appel sur des int devient ambigu. Avec le ::, plus d'ambiguïté. Ce comportement vient de libc++ ; à vérifier avec le compilateur de ton école.

04

ex00 · swap, min, max« Start with a few functions » (sujet, p. 8)

En clair. Trois templates de fonction. swap échange les valeurs de deux paramètres et ne renvoie rien. min renvoie la plus petite des deux valeurs, max la plus grande, et si elles sont égales, les deux renvoient la seconde (p. 8). Les deux arguments doivent avoir le même type, et ce type doit supporter tous les opérateurs de comparaison (p. 8).

Fichiers à rendre (p. 8) : Makefile, main.cpp, whatever.{h, hpp}, dans ex00/.

ex00/whatever.hpp · squelette
#ifndef WHATEVER_HPP
#define WHATEVER_HPP

template <typename T>
void swap(T &a, T &b) { /* à toi */ }

template <typename T>
const T &min(const T &a, const T &b) { /* à toi */ }

template <typename T>
const T &max(const T &a, const T &b) { /* à toi */ }

#endif

Les noms swap, min, max sont imposés ; les noms des paramètres sont libres. Le sujet ne fixe pas le type de retour de min et max : renvoyer une référence const vers l'un des arguments évite une copie, et permet de vérifier quel argument est sorti en comparant des adresses (conseil, pas une règle).

Le cas des valeurs égales

C'est le détail qui fait échouer. Selon la façon d'écrire la comparaison, tu renvoies le premier ou le second argument quand les deux sont égaux. Avec des int, tu ne verras jamais la différence : deux 42 sont indiscernables. Pour la voir, teste avec un type dont la comparaison ne regarde qu'une partie de l'objet. La démo ci-dessous le fait : chaque variable porte une clé, seule comparée, et une étiquette qui permet de reconnaître l'objet renvoyé.

Pour tes propres tests, un petit type suffit (un test, pas une solution) :

main.cpp · un type de test
struct Item
{
	int			key;
	std::string	label;
	bool operator<(const Item &o) const { return key < o.key; }
	bool operator>(const Item &o) const { return key > o.key; }
};

Avec deux Item de clé 5 et d'étiquettes différentes, regarde l'étiquette renvoyée par ::min et par ::max : c'est celle du second argument (vérifié en compilant).

Démo : deux variables, chacune avec une clé (comparée) et une étiquette (ignorée), et trois appels ::swap, ::min, ::max. Cas de contrôle :

a = 2, b = 3 : après ::swap(a, b), a = 3, b = 2 ; min(a, b) = 2 ; max(a, b) = 3.

c = chaine1, d = chaine2 : après ::swap(c, d), c = chaine2, d = chaine1 ; min(c, d) = chaine1 ; max(c, d) = chaine2.

Clés égales (5 et 5), étiquettes « première » et « seconde » : min et max renvoient tous les deux la seconde.

Le résultat attendu

Le sujet donne un main et la sortie qu'il doit produire (p. 9). Ses appels commencent ainsi :

main du sujet (p. 9) · début
int a = 2;
int b = 3;
::swap( a, b );
std::cout << "a = " << a << ", b = " << b << std::endl;

et la sortie annoncée est :

sortie annoncée (p. 9)
a = 3, b = 2
min(a, b) = 2
max(a, b) = 3
c = chaine2, d = chaine1
min(c, d) = chaine1
max(c, d) = chaine2
⚠️

Le sujet n'est pas cohérent au caractère près. Dans le main de la p. 9, les messages sont écrits "min( a, b ) = " (avec des espaces dans les parenthèses), alors que la sortie annoncée montre min(a, b) = 2. Compilé tel quel, le main du sujet affiche la forme avec espaces ; les valeurs sont les bonnes. À vérifier avec ton évaluateur si une comparaison au caractère près t'inquiète.

🧪

Ce que ton main devrait tester. Le main du sujet (int puis std::string) ; un autre type que ceux du sujet (double, char) ; deux valeurs égales avec un type à clé et étiquette, pour voir que le second est renvoyé.

ex01 · iter« Iter » (sujet, p. 10)

En clair. Un template de fonction iter à trois paramètres, qui ne renvoie rien (p. 10) : (1) l'adresse d'un tableau, (2) sa longueur, « passed as a const value », (3) une fonction appelée sur chaque élément. Il doit marcher avec n'importe quel type de tableau, et le troisième paramètre peut être un template de fonction instancié. La fonction passée peut prendre son argument par référence const ou non const, « depending on the context ».

Fichiers à rendre (p. 10) : Makefile, main.cpp, iter.{h, hpp}, dans ex01/. Le sujet demande aussi un main.cpp avec tes tests, assez complet pour produire un exécutable de test.

Les trois paramètres

1L'adresse du tableau : un pointeur T *. Le compilateur déduit T du tableau. Pour un const int[3], il déduit T = const int : c'est ainsi que le même template accepte les tableaux const.
2La longueur, const. Un const sur un paramètre passé par valeur ne change pas la signature (vérifié : void g(std::size_t) et void g(const std::size_t) sont la même fonction) ; il t'interdit seulement de modifier la longueur dans la fonction. Si tu choisis int au lieu de std::size_t (de <cstddef>), compare-la avec un compteur de même signe : sinon -Wsign-compare devient une erreur avec -Werror.
3La fonction. C'est le paramètre difficile : son type doit accepter une fonction ordinaire, un template instancié comme print<int>, une référence const ou non, sur un tableau const ou non.

Trois façons de typer le troisième paramètre

« Think carefully about how to support both const and non-const elements » (p. 10) : c'est la phrase clé de l'exercice. Il y a au moins trois candidates. A : un second paramètre de template F pour la fonction, quelle qu'elle soit. B : un pointeur de fonction void (*)(T &). C : deux surcharges, l'une avec T * et void (*)(T &), l'autre avec const T * et void (*)(const T &). La démo les a toutes compilées, sur les deux tableaux, avec les trois types de fonction et les trois façons de la passer.

Démo : « le compilateur accepte-t-il cet appel ? ». Chaque verdict vient d'un programme compilé avec Apple clang 17 (c++ -std=c++98 -Wall -Wextra -Werror). Cas de contrôle :

const int tab[3] et une fonction void f(int &) : ✗ (avec la signature A : error: binding reference of type 'int' to value of type 'const int' drops 'const' qualifier).

int tab[3] et une fonction void f(const int &) : ✓ avec les signatures A et C, ✗ avec B.

Un template instancié f<int> (fonction const T &) : ✓ avec la signature A, sur les deux tableaux.

Ce que la table de la démo montre, avec Apple clang :

AParamètre générique F. La plus souple : fonction ordinaire, template instancié, référence const ou non, par valeur. Elle ne refuse que ce que le corps refuse (donner un const à une fonction qui le modifie) et un nom de template seul.
Bvoid (*)(T &). Une seule forme de fonction passe. Un tableau const donne T = const int d'un côté et int de l'autre : conflit. Une fonction const T & sur un tableau modifiable : conflit aussi.
CDeux surcharges. Une fonction T & passe sur un tableau modifiable, une fonction const T & passe sur les deux. Une fonction par valeur est refusée, sauf dans un cas curieux de nom de template seul.
💡

Le troisième paramètre peut être un template instancié (p. 10). iter(tab, 3, print<int>) passe l'adresse de la version de print fabriquée pour int. Écrire iter(tab, 3, print), le nom du template sans <int>, échoue avec la signature A : couldn't infer template argument 'F'. Tu verras aussi des cas où des signatures plus strictes réussissent à choisir la bonne version toutes seules ; mieux vaut écrire <int>.

Il n'y a pas de réponse unique : choisis une signature, teste les cas du sujet (tableau const ou non, référence const ou non, template instancié), et sois capable d'expliquer ce que ta signature refuse.

ex01/main.cpp · idées de tests
template <typename T>
void print(const T &x) { std::cout << x << " "; }

int         numbers[3] = {1, 2, 3};
const int   fixed[3]   = {4, 5, 6};

iter(numbers, 3, print<int>);   // tableau modifiable, template instancié
iter(fixed, 3, print<int>);     // tableau const
iter(numbers, 0, print<int>);   // longueur 0 : rien ne doit arriver

Ajoute un tableau d'un autre type (std::string, double) et une fonction qui modifie les éléments. Le sujet n'impose pas de sortie pour cet exercice : ton main doit seulement montrer que tout marche.

ex02 · Array« Array » (sujet, p. 11)

En clair. Une classe template Array<T> qui contient des éléments de type T (p. 11) : un constructeur sans paramètre (tableau vide), un constructeur avec un unsigned int n (n éléments « initialisés par défaut »), une copie par constructeur et par operator= après laquelle l'original et la copie sont indépendants, un accès par [] qui lève une std::exception hors bornes, et une fonction membre size().

Fichiers à rendre (p. 11) : Makefile, main.cpp, Array.{h, hpp}, et, facultatif, Array.tpp, dans ex02/.

ex02/Array.hpp · squelette
#ifndef ARRAY_HPP
#define ARRAY_HPP

#include <cstddef>
#include <exception>

template <typename T>
class Array
{
	private:
		T				*_data;
		unsigned int	_size;

	public:
		Array();                                // tableau vide
		Array(unsigned int n);                  // n éléments « par défaut »
		Array(const Array &other);              // copie profonde
		Array &operator=(const Array &other);   // copie profonde
		~Array();

		T				&operator[](unsigned int i);
		const T			&operator[](unsigned int i) const;
		unsigned int	size() const;

		class OutOfBoundsException : public std::exception
		{
			public:
				virtual const char *what() const throw();
		};
};

#include "Array.tpp"   // facultatif : les définitions peuvent aussi rester ici

#endif

Seuls Array, size(), [] et le type unsigned int du constructeur viennent du sujet ; le nom et le nombre des attributs, le nom de l'exception sont libres. Comme dans tout le module, la classe est en forme canonique orthodoxe (p. 4) : constructeur par défaut, constructeur de copie, operator=, destructeur.

Construire : new[], « par défaut », pas d'avance

Le sujet impose operator new[] et interdit l'allocation préventive (réserver de la place en avance, p. 11) : Array(n) alloue exactement n éléments, et ton programme « must never access non-allocated memory ». « Initialisés par défaut » : le sujet te conseille d'essayer int * a = new int(); puis d'afficher *a (p. 11). Voici ce que donne clang sur macOS :

terminal · clang, c++98
new int()       -> 0
new int[5]()    -> 0 0 0 0 0
new string[3]() -> [][][]
new int[5]      -> -1431655766 -1431655766 ...   (avec MallocPreScribble=1)

Les parenthèses vides () font la différence : avec elles, un int vaut 0 et une std::string est vide (le constructeur par défaut de T est appelé). Sans elles, les int sont indéterminés : les lire est un comportement indéfini. Une valeur propre peut sortir par chance ; la variable d'environnement macOS MallocPreScribble=1 remplit la mémoire neuve avec un motif et montre la vérité (-1431655766 est 0xAAAAAAAA).

Conséquence : un T sans constructeur par défaut ne peut pas être stocké. Vérifié : Array<NoDefault> a(3); donne error: no matching constructor for initialization of 'NoDefault[]'. En revanche, Array<NoDefault> a; seul compile : le compilateur ne fabrique que les fonctions membres que le programme utilise.

Copier : profond, pour de vrai

« Modifying either the original array or its copy after copying musn't affect the other array » (p. 11) : copie profonde, en deux endroits, le constructeur de copie et operator=. Si tu laisses le compilateur générer la copie, il recopie le pointeur _data : les deux tableaux partagent les mêmes cases, et chaque destructeur fait delete[] sur la même adresse. Avec clang sur macOS, le programme meurt avec Trace/BPT trap: 5 ; c'est un comportement indéfini, le symptôme change selon le système. La démo montre les deux versions côte à côte.

Pour operator=, pense à trois choses : l'auto-affectation (a = a : si tu libères l'ancien tableau avant de copier, tu copies depuis de la mémoire libérée) ; l'ancien contenu (à libérer, sinon fuite) ; la taille (la cible peut avoir une taille différente). Dans un test, clang refuse un a = a; écrit tel quel (-Wself-assign-overloaded avec -Wall) : passe par une référence, Array<int> &alias = a; a = alias;.

Accéder : [] en deux versions, et une exception

operator[] renvoie une référence T &, sinon a[0] = 5 ne compile pas (expression is not assignable). Il en faut une seconde, const, renvoyant const T & : sans elle, un tableau reçu par const Array<int> & ne peut pas être lu (no viable overloaded operator[] for type 'const Array<int>'). Les deux testent l'indice : s'il est hors bornes, elles lancent une exception (p. 11). Le sujet écrit « an std::exception is thrown » : une classe imbriquée qui hérite de std::exception en est une, et catch (std::exception &e) la rattrape (vérifié) ; lancer directement std::exception() marche aussi. En C++98, what() garde la signature virtual const char *what() const throw();.

Le paramètre est un unsigned int : un indice négatif y est converti. a[-1] devient a[4294967295] (vérifié), donc « hors bornes » et ton test le rattrape, à condition de comparer avec >= à la taille sans convertir en int. Attention aussi aux boucles de test : for (int i = 0; i < a.size(); i++) ne compile pas avec -Werror (comparison of integers of different signs) ; prends un unsigned int.

Mesurer : size() et le fichier .tpp

size() ne prend aucun paramètre et ne doit pas modifier l'instance (p. 11) : elle est const. Sans const, un tableau reçu en const Array<int> & ne peut pas appeler size() ('this' argument to member function 'size' has type 'const Array<int>', but function is not marked const).

Pour le fichier facultatif Array.tpp (p. 11) : il reçoit les définitions des fonctions membres, ton Array.hpp l'inclut en dernière ligne avant le #endif, et le Makefile ne le compile pas (ce n'est pas un .cpp). Pour l'exception imbriquée : un membre d'un template reste « templaté », donc what() peut vivre dans le .tpp ; une classe d'exception libre définie dans le .hpp avec un corps serait, elle, une implémentation dans un en-tête (règle de la p. 4) : à vérifier avec ton évaluateur.

Démo : deux tableaux a et b en cases, avec un mode « copie superficielle (fausse) » et un mode « copie profonde ». Cas de contrôle :

Array<int>(5) : 5 cases, toutes à 0 (new int[5]()).

Copie profonde puis modification de la copie : l'original ne change pas. Copie superficielle : les deux tableaux changent ensemble, et la fin de portée signale une double libération.

a[5] sur 5 cases : exception std::exception. size() d'un tableau vide : 0.

🧪

Ce que ton main devrait tester. Un tableau vide (size() vaut 0, [0] lève) ; Array<int>(5) avec ses cinq zéros ; un Array<std::string> ; une copie puis une modification de la copie, avec l'original qui ne bouge pas ; une affectation, y compris sur un tableau déjà rempli ; un indice égal à la taille et un indice négatif ; la lecture par un const Array<T> & ; l'absence de fuite.

Étape par étape

Un ordre qui limite les allers-retours : chaque exercice réutilise l'idée du précédent.

1Prépare le terrain. Un dossier par exercice (ex00/, ex01/, ex02/, p. 3), un Makefile qui compile avec -Wall -Wextra -Werror -std=c++98 et ne relink pas, des en-têtes avec gardes d'inclusion. Pas de using namespace, pas de <algorithm>.
2ex00. Écris swap, min, max dans whatever.hpp. Compile d'abord avec le main du sujet (p. 9) et compare les valeurs. Ajoute ensuite un type à clé et étiquette pour vérifier le cas des valeurs égales.
3ex01, un cas à la fois. Fais marcher iter avec un int[] modifiable et une fonction par référence. Puis le tableau const, la référence const, le template instancié, un autre type d'éléments, une longueur nulle. Chaque cas qui casse t'apprend quelque chose sur ta signature.
4ex02, le squelette d'abord. Déclare la classe, le constructeur par défaut et size() : un tableau vide qui compile. Ajoute Array(n) et [] avec le test de bornes et l'exception.
5La copie. Constructeur de copie, puis operator= (auto-affectation, ancien contenu, nouvelle taille). Teste en modifiant la copie, puis l'original.
6La surcharge const. Ajoute le second operator[] et teste-le avec une fonction qui reçoit un const Array<int> &.
7Contrôle final. Un test avec un Array<std::string>, puis la mémoire : leaks --atExit -- ./array sous macOS (il affiche « 0 leaks » quand tout est libéré), valgrind sous Linux. Lance make deux fois : le second ne doit rien refaire. Vérifie les noms des fichiers et des dossiers (p. 12).
08

Pièges classiques

⚠️

Un template défini dans un .cpp. Chaque fichier compile, puis l'édition de liens échoue : Undefined symbols … "void swap<int>(int&, int&)" sous macOS (vérifié). Le corps doit être visible là où le template est appelé : dans le .hpp (p. 8), ou dans un .tpp inclus par lui (p. 11).

⚠️

min ou max qui renvoie le premier quand les valeurs sont égales. Le sujet veut le second (p. 8). Ça dépend de la façon d'écrire le test : sur un type à clé et étiquette, un test écrit « à l'envers » renvoie la première étiquette (vérifié en compilant). Avec des int, tu ne le verras jamais : teste avec un type où l'on voit la différence.

⚠️

Un swap sans valeur temporaire. Deux affectations, a = b; b = a;, écrasent la première valeur : avec 2 et 3, on obtient a = 3, b = 3 (vérifié). Il faut conserver une des deux valeurs avant de l'écraser.

⚠️

Appeler sans ::, ou avec deux types. min(c, d) sur des std::string est ambigu avec std::min (clang, libc++). ::min(a, 3.5) avec un int et un double ne compile pas : les deux arguments doivent avoir le même type (p. 8).

⚠️

Un iter qui refuse un tableau const. Si le troisième paramètre est typé void (*)(T &), un const int[3] ne passe pas : T est const int d'un côté, int de l'autre. Et passer le nom d'un template sans <int> échoue avec un paramètre générique F. La démo montre chaque cas.

⚠️

Une longueur non const (ex01). Le sujet la veut « passed as a const value » (p. 10). Elle ne change pas la signature, mais ton évaluateur la regardera. Et un int comparé à un compteur std::size_t ne compile pas avec -Werror (-Wsign-compare).

⚠️

Copier le pointeur au lieu des cases. Copie superficielle : deux Array partagent le même _data, et le second destructeur fait un delete[] sur une adresse déjà libérée. Avec clang sur macOS, le programme meurt avec Trace/BPT trap: 5. Le sujet exige l'indépendance de la copie (p. 11).

⚠️

Un operator= qui oublie l'auto-affectation. Si tu libères l'ancien tableau avant de copier, a = a copie depuis de la mémoire libérée. Un essai affiche « 0 0 0 » au lieu de « 1 2 3 », et des valeurs de motif avec MallocScribble=1. Teste avec une référence : clang refuse un a = a; littéral.

⚠️

Allouer en avance, ou sortir des bornes. L'allocation préventive est interdite et le programme ne doit jamais accéder à de la mémoire non allouée (p. 11). Un operator[] sans test de bornes lit ou écrit hors du tableau : comportement indéfini, pas d'exception.

⚠️

Les const oubliés. Un size() non const ne s'appelle pas sur un tableau const ; un seul operator[] non const ne se lit pas sur un tableau const ; un operator[] qui renvoie T par valeur ne permet pas a[0] = 5. Les trois erreurs ont été reproduites avec clang.

⚠️

L'indice négatif. a[-1] est converti en unsigned int : 4294967295 avec 32 bits. Ton test de bornes doit rester correct pour cette valeur : elle est ≥ à la taille, donc exception.

⚠️

Un T sans constructeur par défaut. Array<T>(n) n'existe alors pas : new T[n]() ne compile pas. Le constructeur sans paramètre, lui, compile (vérifié) puisque le corps de Array(n) n'est pas fabriqué.

09

Comment je l'ai fait

J'ai suivi l'ordre du sujet. Pour ex00, un seul en-tête avec trois fonctions qui prennent et renvoient des références const ; mon main reprend celui du sujet, puis ajoute des double, des char et deux valeurs égales dont je compare l'adresse à celle du second argument. Pour ex01, iter a deux paramètres de template, le type des éléments et celui de la fonction : c'est ce qui accepte un tableau const, une référence et un template instancié comme print<int>. Pour ex02, Array.hpp inclut Array.tpp à la fin. Le constructeur à n éléments utilise new T[n]() ; la copie est profonde ; operator= construit le nouveau buffer avant de libérer l'ancien et protège l'auto-affectation ; les deux operator[] lèvent la même exception imbriquée. Mon test compare un Array à un tableau miroir de 750 entiers, plus le cas vide, une copie et un accès hors bornes.

📌 À retenir (défense d'éval)

  • ✓
    Les templates vont dans les en-têtes. « Templates must be defined in the header files » (p. 8) ; c'est la seule implémentation tolérée dans un .hpp (p. 4). Un .cpp donne une erreur de lien.
  • ✓
    Le compilateur fabrique une version par type utilisé. T est déduit des arguments ; deux arguments de types différents sont refusés.
  • ✓
    Pourquoi :: ? Il limite la recherche au global : ton swap, pas celui de std (ambiguïté sinon). Et <algorithm> est interdit avant le module 08.
  • ✓
    Valeurs égales : le second. min et max renvoient le second argument (p. 8) ; une référence const permet de le vérifier.
  • ✓
    iter : adresse, longueur const, fonction (p. 10). Il doit accepter les éléments const ou non, une référence const ou non, un template instancié (print<int>). Sache dire ce que ta signature refuse.
  • ✓
    Array : new[], pas d'allocation préventive (p. 11). new T[n]() initialise par défaut (0 pour un int) ; sans (), les int sont indéterminés.
  • ✓
    Copie profonde, deux fois. Constructeur de copie et operator= : original et copie indépendants (p. 11). operator= gère l'auto-affectation et libère l'ancien contenu.
  • ✓
    operator[] en deux versions (const et non const), avec test de bornes et std::exception (p. 11). Un indice négatif devient un grand unsigned int : hors bornes aussi.
  • ✓
    size() est const, sans paramètre (p. 11).
  • ✓
    Hygiène. c++ -Wall -Wextra -Werror -std=c++98, forme canonique, gardes d'inclusion, pas de using namespace, pas de STL, aucune fuite. Une petite modification peut être demandée en défense (p. 12).
