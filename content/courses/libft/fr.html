Projet 42 · Fondations C

Le projet libft

Réécrire ta propre bibliothèque C : des fonctions de la libc, des utilitaires et des listes chaînées. Ce qu'il faut comprendre avant d'écrire la première ligne.

libft.a · cc -Wall -Wextra -Werror · ar rcs · la Norme

01

Le projet en bref

libft est le premier projet de code du tronc commun : tu construis ta propre bibliothèque statique, libft.a. Les projets suivants du tronc commun peuvent la réutiliser (chaque sujet indique si c'est autorisé) : ce que tu écris ici te sert longtemps.

On te demande trois choses : refaire des fonctions de la libc (même prototype, même comportement, préfixe ft_), écrire des utilitaires qui n'existent pas dans la libc, et, en bonus, manipuler des listes chaînées.

Rien de magique là-dedans : chaque fonction est une petite boucle sur des octets. Ce qui fait réussir ou échouer en correction, c'est le détail aux limites : une taille de 0, un pointeur nul, un malloc qui échoue, un entier qui déborde.

📖

Ton référentiel, c'est le sujet et les pages de man. Avant chaque fonction, lis sa ligne de description dans le sujet et sa page de man (man 3 strlcpy). Ce cours t'aide à comprendre les points délicats ; il ne remplace pas ce travail.

03

Partie 1 : la libc refaite

La consigne tient en une phrase : mêmes prototypes, mêmes comportements, seul le nom change. Le man de chaque fonction est donc ton cahier des charges. Certaines pages de man déclarent leurs prototypes avec restrict : ne le recopie pas. Et strlcpy, strlcat et strnstr viennent des systèmes BSD : leur page n'est pas toujours installée sous Linux, cherche-la en ligne si besoin.

FonctionComme la vraie libc… et ce qu'il faut surveiller
ft_isalpha, ft_isdigit, ft_isalnum, ft_isascii, ft_isprintElles prennent un int et renvoient une valeur non nulle si le test est vrai, 0 sinon. Ne suppose pas que « vrai » vaut 1.
ft_toupper, ft_tolowerReçoivent et renvoient un int. Ce qui n'est pas une lettre revient tel quel.
ft_memset, ft_bzeroRemplissent n octets. Le int c de memset est converti en unsigned char ; bzero ne renvoie rien.
ft_memcpyCopie n octets. Le man précise que les zones ne doivent pas se chevaucher.
ft_memmoveMême signature, mais le résultat doit être correct même si les zones se chevauchent. C'est le point de la démo plus bas.
ft_memchr, ft_memcmpTravaillent sur n octets, pas sur des chaînes : un '\0' n'arrête rien. La comparaison se fait en unsigned char.
ft_strlenRenvoie un size_t.
ft_strchr, ft_strrchrCherchent c (un int converti en char). Chercher '\0' est valide : le résultat pointe sur le terminateur.
ft_strncmpCompare au plus n caractères, en unsigned char.
ft_strnstrCherche little dans les len premiers caractères de big. Si little est vide, renvoie big ; s'il est introuvable, renvoie NULL.
ft_strlcpy, ft_strlcatCopient ou concatènent en respectant une taille, et le \0 final est posé dès qu'il y a de la place (size > 0 pour strlcpy, size > strlen(dst) pour strlcat). Elles renvoient la longueur qu'elles voulaient obtenir, pas ce qu'elles ont écrit (détail ci-dessous).
ft_atoiSaute les espaces, lit un signe optionnel puis des chiffres, s'arrête au premier caractère invalide. Aucune gestion d'erreur : rien de valide donne 0.
ft_callocAlloue nmemb * size octets, tous mis à 0. Si la multiplication déborde, il faut renvoyer NULL.
ft_strdupAlloue la longueur de la chaîne plus un, copie, et renvoie NULL si malloc échoue.

strlcpy et strlcat : la valeur de retour

Ces deux fonctions renvoient la longueur totale qu'elles ont essayé de créer. Pour strlcpy, c'est la longueur de src. Pour strlcat, c'est la longueur initiale de dst (plafonnée à size) plus celle de src. Résultat : retour >= size signifie « tronqué ». Quelques cas pour te repérer (dans le dernier, size est inférieur ou égal à la longueur de dst : rien n'est ajouté, et le retour vaut size plus la longueur de src) :

cas à reproduire dans ton main
// strlcpy(dst, "hello", size)
size 3 → "he"        retour 5  tronqué
size 8 → "hello"     retour 5
size 0 → rien écrit  retour 5

// strlcat(dst, "cdef", size)
// avec dst = "ab" au départ
size 8 → "abcdef"   retour 6
size 5 → "abcd"     retour 6  tronqué
size 1 → "ab"       retour 5  inchangé

memmove : le sens de la copie

Si tu copies toujours du premier octet vers le dernier, tu peux lire un octet que ta propre copie vient d'écraser : c'est le cas quand la destination commence à l'intérieur de la source. memmove doit se comporter comme si les octets passaient par un tampon intermédiaire. La parade tient en un test sur les adresses : si dst est après src, copie depuis la fin ; sinon, depuis le début. Essaie les deux sens :

Démo : un tableau de 10 octets A B C D E F G H I J. On copie n = 6 octets depuis src = 0 vers dst = 3, les zones se chevauchent.

Copie avant : A B C A B C A B C J (corrompu : les octets A, B, C sont relus après avoir été recopiés). Copie arrière : A B C A B C D E F J (correct).

On travaille octet par octet, sur des unsigned char. Le schéma tient en quelques lignes ; à toi d'écrire les boucles :

ft_memmove.c · idée
unsigned char       *d = (unsigned char *)dst;
const unsigned char *s = (const unsigned char *)src;
// d après s : de la fin vers le début
// sinon     : du début vers la fin
04

Partie 2 : les utilitaires

Ces fonctions n'existent pas dans la libc, ou pas sous cette forme. Presque toutes allouent : le sujet précise qu'elles utilisent malloc et qu'elles renvoient NULL si l'allocation échoue. Pour chacune, le sujet liste aussi les fonctions externes que tu as le droit d'appeler (malloc, free ou write selon le cas) : relis cette ligne avant de coder.

FonctionCe que dit le sujet, et ce qu'il faut en retenir
ft_substrchar *ft_substr(char const *s, unsigned int start, size_t len)
Sous-chaîne de s qui commence à l'indice start, de taille maximale len. Que faire si start dépasse la fin de s ? Le sujet ne le dit pas : l'usage courant est de renvoyer une chaîne vide (pas NULL). Choisis, et sois prêt à défendre ton choix.
ft_strjoinchar *ft_strjoin(char const *s1, char const *s2)
Nouvelle chaîne : s1 puis s2. Compte le \0 dans la taille allouée.
ft_strtrimchar *ft_strtrim(char const *s1, char const *set)
Copie de s1 sans les caractères de set au début et à la fin. set est un ensemble de caractères, pas une sous-chaîne à retirer. Cas à tester : s1 composée uniquement de caractères du set, qui donne une chaîne vide.
ft_splitchar **ft_split(char const *s, char c)
Tableau de chaînes obtenu en découpant s avec le délimiteur c. Le tableau se termine par un pointeur NULL. La plus riche du projet : voir plus bas.
ft_itoachar *ft_itoa(int n)
Chaîne qui représente l'entier, négatifs compris. Calcule la taille avant d'allouer : nombre de chiffres, plus un pour le signe si besoin, plus un pour le \0. Cas à tester : 0 et INT_MIN.
ft_strmapichar *ft_strmapi(char const *s, char (*f)(unsigned int, char))
Applique f à chaque caractère (son indice, puis le caractère) et range les résultats dans une nouvelle chaîne. s n'est pas modifiée.
ft_striterivoid ft_striteri(char *s, void (*f)(unsigned int, char*))
Même idée, mais chaque caractère est passé par adresse : f modifie s en place. Rien à allouer, rien à renvoyer.
ft_putchar_fd, ft_putstr_fd, ft_putendl_fd, ft_putnbr_fdvoid ft_putchar_fd(char c, int fd) et ses trois cousines (char *s pour les deux chaînes, int n pour le nombre). Elles écrivent sur le descripteur fd ; putendl ajoute un \n. Seule fonction externe permise : write, donc pas de printf.

ft_split : un tableau de chaînes à construire

Découpe le travail en quatre temps : compter les mots (un mot est une suite de caractères différents de c), allouer le tableau de « mots + 1 » pointeurs, puis pour chaque mot mesurer, allouer, copier, et enfin poser le NULL final. Des séparateurs répétés, en tête ou en queue ne produisent jamais de mot vide. Voilà ce que tu dois obtenir en mémoire :

ft_split("hello world 42", ' ')
tab ──> [ • ][ • ][ • ][NULL]
          │    │    │
          │    │    └──> "42\0"
          │    └───────> "world\0"
          └────────────> "hello\0"

Trois mots, donc 4 appels à malloc : un par mot, plus un pour le tableau. Le NULL n'est pas une allocation, c'est la valeur de la dernière case. Joue avec la démo :

Démo : le champ de texte et le séparateur donnent la liste des mots que ft_split doit renvoyer, leur nombre et le nombre de malloc.

" hello world 42 " avec ' ' donne hello, world, 42 (3 mots, 4 malloc). ",,a,,b," avec ',' donne a, b (2 mots). La chaîne vide donne 0 mot et un tableau qui ne contient que NULL.

⚠️

Et si un malloc échoue au milieu ? Les mots déjà alloués doivent être libérés avant de renvoyer NULL : voir les pièges.

05

Bonus : les listes chaînées

Le bonus ajoute à ton libft.h la structure que donne le sujet, puis neuf fonctions pour la manipuler :

libft.h
typedef struct s_list
{
	void			*content;
	struct s_list	*next;
}	t_list;

content porte la donnée (un void * accepte n'importe quel type) ; next est l'adresse du nœud suivant, ou NULL si c'est le dernier.

FonctionRôle
ft_lstnewt_list *ft_lstnew(void *content)
Alloue un nœud : content reçoit la valeur donnée, next vaut NULL.
ft_lstadd_frontvoid ft_lstadd_front(t_list **lst, t_list *new)
Ajoute new au début de la liste.
ft_lstsizeint ft_lstsize(t_list *lst)
Compte les nœuds.
ft_lstlastt_list *ft_lstlast(t_list *lst)
Renvoie le dernier nœud.
ft_lstadd_backvoid ft_lstadd_back(t_list **lst, t_list *new)
Ajoute new à la fin de la liste.
ft_lstdelonevoid ft_lstdelone(t_list *lst, void (*del)(void *))
Libère le contenu avec del, puis le nœud avec free. La mémoire de next n'est pas libérée.
ft_lstclearvoid ft_lstclear(t_list **lst, void (*del)(void *))
Supprime le nœud donné et tous ses successeurs, puis met le pointeur de liste à NULL.
ft_lstitervoid ft_lstiter(t_list *lst, void (*f)(void *))
Applique f au contenu de chaque nœud.
ft_lstmapt_list *ft_lstmap(t_list *lst, void *(*f)(void *), void (*del)(void *))
Applique f au contenu de chaque nœud et construit une nouvelle liste avec les résultats. del sert à détruire un contenu si besoin. NULL si une allocation échoue.

Pourquoi un double pointeur ?

En C, un argument est passé par copie. Si ft_lstadd_front recevait seulement un t_list *, elle changerait sa copie de la tête et l'appelant ne verrait rien. Avec un t_list **, elle reçoit l'adresse du pointeur de l'appelant et peut le modifier. Même raison pour ft_lstclear, qui doit remettre la tête à NULL.

utilisation
t_list	*head;

head = NULL;
// &head : la fonction peut modifier head
ft_lstadd_back(&head, ft_lstnew(content));

Construis une liste, double ses valeurs avec ft_lstmap, vide-la avec ft_lstclear. Les compteurs malloc et free montrent ce que ta liste a vraiment alloué : décoche la case pour voir ce que coûte l'oubli de libérer l'ancienne liste.

Démo : une liste d'entiers que l'on construit avec ft_lstadd_front et ft_lstadd_back.

Séquence de contrôle : add_back 1, add_back 2, add_front 0 donnent 0 → 1 → 2 → NULL (taille 3). ft_lstmap (×2) donne 0 → 2 → 4 → NULL. ft_lstclear vide la liste.

Étape par étape

Un ordre qui limite les allers-retours : chaque étape s'appuie sur ce que tu viens d'écrire.

Les testeurs écrits par la communauté complètent tes tests, ils ne les remplacent pas.

Un Makefile qui ne relink pas

Un « relink » : make refait l'archive alors que rien n'a changé. Pour l'éviter, la règle de l'archive dépend des fichiers objets, et chaque objet de son .c ; make ne reconstruit alors que ce qui est plus ancien que sa source.

Makefile · squelette
NAME = libft.a
CFLAGS = -Wall -Wextra -Werror
SRCS = ft_atoi.c ft_bzero.c ...
OBJ = $(SRCS:.c=.o)

all: $(NAME)

# dépend des .o : aucun .o modifié, aucune nouvelle archive
$(NAME): $(OBJ)
	ar rcs $(NAME) $(OBJ)

%.o: %.c libft.h
	$(CC) $(CFLAGS) -c $< -o $@

Le test est simple : lance make deux fois de suite. La seconde fois, il doit répondre qu'il n'y a rien à faire pour all. Fais le même essai avec make bonus.

07

Pièges classiques

⚠️

Un malloc échoue en plein milieu. Dans ft_split, si l'allocation du troisième mot échoue, les deux premiers et le tableau existent déjà. Il faut libérer chaque mot déjà alloué, puis le tableau, avant de renvoyer NULL ; sinon c'est une fuite. Même logique dans ft_lstmap (la nouvelle liste en cours de construction) et partout où tu enchaînes deux allocations. Teste le retour de chaque malloc.

⚠️

Un size_t ne descend jamais sous zéro. Il est non signé : 0 moins 1 donne la plus grande valeur possible, pas -1.

piege.c
size_t	i;

i = 0;
i--;                // SIZE_MAX, pas -1
while (i >= 0)    // toujours vrai
	i--;
⚠️

Cas typiques : size - 1 quand size vaut 0 (ft_strlcpy), len - 1 sur une chaîne vide (ft_strtrim, ft_strrchr), une boucle while (n--) dont tu relis n ensuite. Ces formes indirectes sont le vrai danger : le compilateur ne les signale pas. La forme directe de l'exemple (i >= 0 sur un non signé) dépend du compilateur : GCC la signale avec -Wtype-limits, inclus dans -Wextra, donc refusée avec -Werror ; le clang d'Apple ne dit rien. Comparer un int à un size_t déclenche -Wsign-compare, activé par -Wextra et donc refusé avec -Werror.

⚠️

ft_itoa(INT_MIN). INT_MIN vaut -2147483648 mais INT_MAX seulement 2147483647 : écrire -n sur un int déborde (comportement indéfini). Travaille sur un type plus large (long long a au moins 64 bits). Pense aussi à 0, qui doit donner "0", et à compter le signe dans la taille allouée. La même précaution vaut pour ft_putnbr_fd(-2147483648, fd).

⚠️

ft_atoi et débordement. Le man de atoi ne définit pas le résultat quand la valeur ne tient pas dans un int, et le sujet ne te demande pas d'inventer une règle. Veille quand même à ne pas planter, et à bien lire "-2147483648" : accumuler dans un int dépasse déjà avant d'appliquer le signe, un accumulateur plus large évite cette surprise. Les espaces à sauter sont ceux de isspace (espace, \t, \n, \v, \f, \r) ; un seul signe est lu, donc "+-5" donne 0.

⚠️

ft_strlcpy avec dstsize == 0. Avec une taille nulle, il ne faut rien écrire, pas même le \0, mais renvoyer quand même la longueur de src. L'erreur classique est de poser dst[size - 1] = '\0' sans test : size - 1 vaut alors SIZE_MAX (piège précédent) et tu écris très loin hors de dst.

⚠️

Fuite dans ft_lstclear. Pour chaque nœud : garde next avant de libérer, applique del au contenu, libère le nœud, avance. Oublier del, oublier le free du nœud, ou relire next après le free sont les trois classiques. À la fin, le pointeur de liste doit valoir NULL.

⚠️

ft_calloc et multiplication qui déborde. nmemb * size se calcule en size_t : si le produit dépasse SIZE_MAX, il revient à une petite valeur, malloc réussit et tu rends un bloc trop petit (corruption mémoire à l'usage). Teste avant de multiplier (SIZE_MAX vient de stdint.h) :

ft_calloc.c · l'idée du test
// le produit déborderait ?
if (nmemb != 0 && size > SIZE_MAX / nmemb)
	return (NULL);
⚠️

Un Makefile qui relink. Si une règle all relance ar sans dépendre des objets, ou si $(NAME) est déclarée .PHONY alors qu'elle produit un fichier, make refait l'archive à chaque appel (les objets, eux, ne sont pas recompilés). Teste deux make de suite.

⚠️

Une fonction auxiliaire qui n'est pas static. Elle devient visible de tout le programme : si un autre fichier (ou le projet qui utilisera ta libft) définit le même nom, l'édition de liens échoue (« multiple definition » sous Linux, « duplicate symbol » sous macOS). Le sujet demande des helpers static pour limiter leur portée au fichier.

⚠️

Comparer en char au lieu de unsigned char. Dans ft_memcmp et ft_strncmp, les octets supérieurs à 127 doivent être comparés comme des valeurs de 0 à 255. Avec un char signé, ils deviendraient négatifs et l'ordre serait faux.

08

Comment je l'ai fait

J'ai suivi l'ordre du sujet, en commençant par les fonctions courtes dont les autres dépendent. Mon Makefile range les sources en trois listes (partie 1, partie 2, bonus) ; une règle générique compile chaque fichier avec les trois drapeaux, ar rcs fabrique libft.a, et la règle bonus y ajoute les fonctions de liste. Pour ft_memmove, je compare les deux adresses afin de choisir le sens de la copie. J'ai découpé ft_split en petites fonctions (compter les mots, mesurer le suivant, remplir le tableau) plus un nettoyage qui libère les mots déjà alloués si un malloc échoue. ft_itoa calcule sur un long à cause de INT_MIN, et ft_lstmap vide la nouvelle liste dès qu'un nœud échoue. J'ai testé avec mes propres main, puis avec des testeurs de la communauté.
