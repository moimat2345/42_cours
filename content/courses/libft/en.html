The libft project

Rewrite your own C library: libc functions, utilities and linked lists. What you need to understand before writing the first line.

libft.a · cc -Wall -Wextra -Werror · ar rcs · the Norm

01

The project in short

libft is the first coding project of the common core: you build your own static library, libft.a. The later common-core projects can reuse it (each subject says whether that is allowed): what you write here will be useful to you for a long time.

You are asked for three things: remake libc functions (same prototype, same behavior, ft_ prefix), write utilities that don't exist in the libc, and, as a bonus, handle linked lists.

There is nothing magical about it: every function is a small loop over bytes. What makes you pass or fail during evaluation is the detail at the edges: a size of 0, a null pointer, a malloc that fails, an integer that overflows.

📖

Your reference is the subject and the man pages. Before each function, read its description line in the subject and its man page (man 3 strlcpy). This course helps you understand the tricky points; it doesn't replace that work.

03

Part 1: the libc remade

The instruction fits in one sentence: same prototypes, same behavior, only the name changes. The man page of each function is therefore your specification. Some man pages declare their prototypes with restrict: don't copy it. And strlcpy, strlcat and strnstr come from BSD systems: their page isn't always installed on Linux; look it up online if needed.

FunctionLike the real libc… and what to watch for
ft_isalpha, ft_isdigit, ft_isalnum, ft_isascii, ft_isprintThey take an int and return a non-zero value if the test is true, 0 otherwise. Don't assume "true" is 1.
ft_toupper, ft_tolowerReceive and return an int. Anything that isn't a letter comes back unchanged.
ft_memset, ft_bzeroFill n bytes. The int c of memset is converted to unsigned char; bzero returns nothing.
ft_memcpyCopies n bytes. The man page specifies that the areas must not overlap.
ft_memmoveSame signature, but the result must be correct even if the areas overlap. That's the point of the demo below.
ft_memchr, ft_memcmpWork on n bytes, not on strings: a '\0' stops nothing. The comparison is done as unsigned char.
ft_strlenReturns a size_t.
ft_strchr, ft_strrchrLook for c (an int converted to char). Looking for '\0' is valid: the result points to the terminator.
ft_strncmpCompares at most n characters, as unsigned char.
ft_strnstrLooks for little in the first len characters of big. If little is empty, returns big; if it isn't found, returns NULL.
ft_strlcpy, ft_strlcatCopy or concatenate within a size limit, and the final \0 is set as soon as there is room (size > 0 for strlcpy, size > strlen(dst) for strlcat). They return the length they tried to create, not what they wrote (details below).
ft_atoiSkips whitespace, reads an optional sign then digits, stops at the first invalid character. No error handling: nothing valid gives 0.
ft_callocAllocates nmemb * size bytes, all set to 0. If the multiplication overflows, you must return NULL.
ft_strdupAllocates the length of the string plus one, copies, and returns NULL if malloc fails.

strlcpy and strlcat: the return value

These two functions return the total length they tried to create. For strlcpy, that is the length of src. For strlcat, it is the initial length of dst (capped at size) plus that of src. Result: return >= size means "truncated". A few cases to get your bearings (in the last one, size is less than or equal to the length of dst: nothing is appended, and the return value is size plus the length of src):

cases to reproduce in your main
// strlcpy(dst, "hello", size)
size 3 → "he"             return 5  truncated
size 8 → "hello"          return 5
size 0 → nothing written  return 5

// strlcat(dst, "cdef", size)
// with dst = "ab" at the start
size 8 → "abcdef"   return 6
size 5 → "abcd"     return 6  truncated
size 1 → "ab"       return 5  unchanged

memmove: the direction of the copy

If you always copy from the first byte to the last, you can read a byte that your own copy has just overwritten: that happens when the destination starts inside the source. memmove must behave as if the bytes went through an intermediate buffer. The fix comes down to one test on the addresses: if dst is after src, copy from the end; otherwise, from the start. Try both directions:

Demo: an array of 10 bytes A B C D E F G H I J. We copy n = 6 bytes from src = 0 to dst = 3, the areas overlap.

Forward copy: A B C A B C A B C J (corrupted: the bytes A, B, C are re-read after being copied over). Backward copy: A B C A B C D E F J (correct).

We work byte by byte, on unsigned char. The outline fits in a few lines; writing the loops is up to you:

ft_memmove.c · idea
unsigned char       *d = (unsigned char *)dst;
const unsigned char *s = (const unsigned char *)src;
// d after s : from the end to the start
// otherwise : from the start to the end
04

Part 2: the utilities

These functions don't exist in the libc, or not in this form. Almost all of them allocate: the subject specifies that they use malloc and that they return NULL if the allocation fails. For each one, the subject also lists the external functions you are allowed to call (malloc, free or write as the case may be): re-read that line before coding.

FunctionWhat the subject says, and what to take from it
ft_substrchar *ft_substr(char const *s, unsigned int start, size_t len)
Substring of s that starts at index start, with a maximum size of len. What if start is past the end of s? The subject doesn't say: the common practice is to return an empty string (not NULL). Pick one, and be ready to defend your choice.
ft_strjoinchar *ft_strjoin(char const *s1, char const *s2)
New string: s1 followed by s2. Count the \0 in the allocated size.
ft_strtrimchar *ft_strtrim(char const *s1, char const *set)
Copy of s1 without the characters of set at the start and at the end. set is a set of characters, not a substring to remove. Case to test: s1 made only of characters from set, which gives an empty string.
ft_splitchar **ft_split(char const *s, char c)
Array of strings obtained by splitting s with the delimiter c. The array ends with a NULL pointer. The most involved function of the project: see below.
ft_itoachar *ft_itoa(int n)
String that represents the integer, negatives included. Compute the size before allocating: number of digits, plus one for the sign if needed, plus one for the \0. Cases to test: 0 and INT_MIN.
ft_strmapichar *ft_strmapi(char const *s, char (*f)(unsigned int, char))
Applies f to each character (its index, then the character) and stores the results in a new string. s is not modified.
ft_striterivoid ft_striteri(char *s, void (*f)(unsigned int, char*))
Same idea, but each character is passed by address: f modifies s in place. Nothing to allocate, nothing to return.
ft_putchar_fd, ft_putstr_fd, ft_putendl_fd, ft_putnbr_fdvoid ft_putchar_fd(char c, int fd) and its three variants (char *s for the two strings, int n for the number). They write to the descriptor fd; putendl adds a \n. The only external function allowed: write, so no printf.

ft_split: an array of strings to build

Split the work into four phases: count the words (a word is a run of characters different from c), allocate the array of "words + 1" pointers, then for each word measure, allocate, copy, and finally set the final NULL. Repeated separators, at the start or at the end, never produce an empty word. Here is what you must end up with in memory:

ft_split("hello world 42", ' ')
tab ──> [ • ][ • ][ • ][NULL]
          │    │    │
          │    │    └──> "42\0"
          │    └───────> "world\0"
          └────────────> "hello\0"

Three words, so 4 calls to malloc: one per word, plus one for the array. The NULL is not an allocation, it is the value of the last slot. Play with the demo:

Demo: the text field and the separator give the list of words that ft_split must return, their count and the number of malloc calls.

" hello world 42 " with ' ' gives hello, world, 42 (3 words, 4 malloc). ",,a,,b," with ',' gives a, b (2 words). The empty string gives 0 words and an array that only contains NULL.

⚠️

What if a malloc fails in the middle? The words already allocated must be freed before returning NULL: see the pitfalls.

Bonus: linked lists

The bonus adds to your libft.h the structure given by the subject, then nine functions to manipulate it:

libft.h
typedef struct s_list
{
	void			*content;
	struct s_list	*next;
}	t_list;

content holds the data (a void * accepts any type); next is the address of the next node, or NULL if it is the last one.

FunctionRole
ft_lstnewt_list *ft_lstnew(void *content)
Allocates a node: content receives the given value, next is NULL.
ft_lstadd_frontvoid ft_lstadd_front(t_list **lst, t_list *new)
Adds new at the beginning of the list.
ft_lstsizeint ft_lstsize(t_list *lst)
Counts the nodes.
ft_lstlastt_list *ft_lstlast(t_list *lst)
Returns the last node.
ft_lstadd_backvoid ft_lstadd_back(t_list **lst, t_list *new)
Adds new at the end of the list.
ft_lstdelonevoid ft_lstdelone(t_list *lst, void (*del)(void *))
Frees the content with del, then the node with free. The memory of next is not freed.
ft_lstclearvoid ft_lstclear(t_list **lst, void (*del)(void *))
Deletes the given node and all its successors, then sets the list pointer to NULL.
ft_lstitervoid ft_lstiter(t_list *lst, void (*f)(void *))
Applies f to the content of each node.
ft_lstmapt_list *ft_lstmap(t_list *lst, void *(*f)(void *), void (*del)(void *))
Applies f to the content of each node and builds a new list with the results. del is used to destroy a content if needed. NULL if an allocation fails.

Why a double pointer?

In C, an argument is passed by copy. If ft_lstadd_front received only a t_list *, it would change its copy of the head and the caller would see nothing. With a t_list **, it receives the address of the caller's pointer and can modify it. Same reason for ft_lstclear, which must reset the head to NULL.

usage
t_list	*head;

head = NULL;
// &head: the function can modify head
ft_lstadd_back(&head, ft_lstnew(content));

Build a list, double its values with ft_lstmap, empty it with ft_lstclear. The malloc and free counters show what your list really allocated: uncheck the box to see what forgetting to free the old list costs.

Demo: a list of integers built with ft_lstadd_front and ft_lstadd_back.

Control sequence: add_back 1, add_back 2, add_front 0 give 0 → 1 → 2 → NULL (size 3). ft_lstmap (×2) gives 0 → 2 → 4 → NULL. ft_lstclear empties the list.

06

Step by step

An order that limits back-and-forth: each step builds on what you have just written.

1Set the stage. A libft.h with its include guards, a minimal Makefile (see below) and a test main outside the repository or untracked by git. Run norminette from the very first file.
2Warm-up. The character tests, ft_toupper, ft_tolower and ft_strlen. Short, but they get you used to the Norm.
3Strings. ft_strchr, ft_strrchr, ft_strncmp, ft_strnstr, then ft_strlcpy and ft_strlcat, testing sizes 0, 1 and too small.
4Memory. ft_memset, ft_bzero, ft_memcpy, ft_memmove, ft_memchr, ft_memcmp. Then ft_calloc and ft_strdup, the first functions that allocate.
5Conversion and first allocations of part 2. ft_atoi first, then part 2: ft_substr, ft_strjoin, ft_strtrim, which reuse what you already have.
6Output and function parameters. ft_itoa, ft_strmapi, ft_striteri, the four ft_put*_fd. Keep ft_split for the end: it has the most error handling to get right.
7The complete Makefile. Objects, archive, clean, fclean, re, without relinking.
8The bonus. ft_lstnew, ft_lstadd_front, ft_lstsize, ft_lstlast, ft_lstadd_back, ft_lstdelone, ft_lstclear, ft_lstiter, ft_lstmap, then the bonus rule of the Makefile, which adds these functions to libft.a. Check in your subject whether their files must carry the _bonus suffix.
9Final check. Your own main files with the edge cases, then valgrind or -fsanitize=address on Linux: no leaks, no crashes. On an Apple Silicon Mac, AddressSanitizer's leak detection is not available: use leaks --atExit -- ./a.out instead. Testers written by the community complement your tests; they don't replace them.

A Makefile that doesn't relink

A "relink" is when make rebuilds the archive even though nothing has changed. To avoid it, the archive rule depends on the object files, and each object on its .c; make then only rebuilds what is older than its source.

Makefile · skeleton
NAME = libft.a
CFLAGS = -Wall -Wextra -Werror
SRCS = ft_atoi.c ft_bzero.c ...
OBJ = $(SRCS:.c=.o)

all: $(NAME)

# depends on the .o: no .o modified, no new archive
$(NAME): $(OBJ)
	ar rcs $(NAME) $(OBJ)

%.o: %.c libft.h
	$(CC) $(CFLAGS) -c $< -o $@

The test is simple: run make twice in a row. The second time, it must answer that there is nothing to be done for all. Do the same with make bonus.

07

Classic pitfalls

⚠️

A malloc fails in the middle. In ft_split, if the allocation of the third word fails, the first two and the array already exist. You must free every word already allocated, then the array, before returning NULL; otherwise it's a leak. Same logic in ft_lstmap (the new list under construction) and anywhere you chain two allocations. Check the return value of every malloc.

⚠️

A size_t never goes below zero. It is unsigned: 0 minus 1 gives the largest possible value, not -1.

pitfall.c
size_t	i;

i = 0;
i--;                // SIZE_MAX, not -1
while (i >= 0)    // always true
	i--;
⚠️

Typical cases: size - 1 when size is 0 (ft_strlcpy), len - 1 on an empty string (ft_strtrim, ft_strrchr), a while (n--) loop whose n you read afterward. These indirect forms are the real danger: the compiler doesn't flag them. The direct form in the example (i >= 0 on an unsigned) depends on the compiler: GCC flags it with -Wtype-limits, included in -Wextra, so it is rejected with -Werror; Apple's clang says nothing. Comparing an int with a size_t triggers -Wsign-compare, enabled by -Wextra and therefore rejected with -Werror.

⚠️

ft_itoa(INT_MIN). INT_MIN is -2147483648 but INT_MAX is only 2147483647: writing -n on an int overflows (undefined behavior). Work with a wider type (long long has at least 64 bits). Also think of 0, which must give "0", and of counting the sign in the allocated size. The same precaution applies to ft_putnbr_fd(-2147483648, fd).

⚠️

ft_atoi and overflow. The atoi man page doesn't define the result when the value doesn't fit in an int, and the subject doesn't ask you to invent a rule. Still, make sure you don't crash and that you read "-2147483648" correctly: accumulating in an int already overflows before the sign is applied, and a wider accumulator avoids that surprise. The whitespace to skip is that of isspace (space, \t, \n, \v, \f, \r); only one sign is read, so "+-5" gives 0.

⚠️

ft_strlcpy with dstsize == 0. With a size of zero, you must write nothing, not even the \0, but still return the length of src. The classic mistake is to set dst[size - 1] = '\0' without a test: size - 1 is then SIZE_MAX (previous pitfall) and you write very far outside dst.

⚠️

Leak in ft_lstclear. For each node: keep next before freeing, apply del to the content, free the node, move on. Forgetting del, forgetting the free of the node, or re-reading next after the free are the three classics. At the end, the list pointer must be NULL.

⚠️

ft_calloc and an overflowing multiplication. nmemb * size is computed as a size_t: if the product exceeds SIZE_MAX, it wraps around to a small value, malloc succeeds and you return a block that is too small (memory corruption when it is used). Test before multiplying (SIZE_MAX comes from stdint.h):

ft_calloc.c · the idea of the test
// would the product overflow?
if (nmemb != 0 && size > SIZE_MAX / nmemb)
	return (NULL);
⚠️

A Makefile that relinks. If an all rule re-runs ar without depending on the objects, or if $(NAME) is declared .PHONY although it produces a file, make rebuilds the archive on every call (the objects, for their part, are not recompiled). Test two make in a row.

⚠️

A helper function that isn't static. It becomes visible to the whole program: if another file (or the project that will use your libft) defines the same name, linking fails ("multiple definition" on Linux, "duplicate symbol" on macOS). The subject asks for static helpers to limit their scope to the file.

⚠️

Comparing as char instead of unsigned char. In ft_memcmp and ft_strncmp, bytes above 127 must be compared as values from 0 to 255. With a signed char, they would become negative and the order would be wrong.

08

How I did it

I followed the order of the subject, starting with the short functions the others depend on. My Makefile sorts the sources into three lists (part 1, part 2, bonus); a generic rule compiles each file with the three flags, ar rcs builds libft.a, and the bonus rule adds the list functions to it. For ft_memmove, I compare the two addresses to choose the direction of the copy. I split ft_split into small functions (count the words, measure the next one, fill the array) plus a cleanup that frees the words already allocated if a malloc fails. ft_itoa computes on a long because of INT_MIN, and ft_lstmap empties the new list as soon as a node fails. I tested with my own main files, then with community testers.
