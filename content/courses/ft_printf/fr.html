Projet C · Fonctions variadiques

ft_printf

Recoder printf : comprendre comment une fonction reçoit un nombre variable d'arguments, puis comment elle les affiche en décimal, en hexadécimal et en pointeur.

sujet : ft_printf · libftprintf.a · c s p d i u x X % · -Wall -Wextra -Werror · Norme

01

Le projet en bref

Tu écris une fonction ft_printf qui imite le printf de la libc : elle reçoit une chaîne de format suivie d'un nombre d'arguments qu'elle ne connaît pas à l'avance, écrit le résultat avec write, et renvoie le nombre de caractères écrits.

Le travail tient en trois idées : lire des arguments en nombre variable (stdarg.h), parcourir le format en distinguant le texte des conversions, puis afficher chaque valeur dans la bonne base avec pour seul outil write. Le reste (le Makefile, la bibliothèque libftprintf.a) est de l'outillage.

💡

Ton arbitre, c'est le vrai printf. Le sujet te demande d'imiter printf : pour chaque cas, compare sa sortie et sa valeur de retour avec les tiennes.

03

Les arguments variables

Dans le prototype int ft_printf(const char *, ...);, les trois points disent au compilateur : « il peut y avoir n'importe quoi ensuite ». Il ne vérifie rien, et ta fonction ne sait pas non plus combien d'arguments elle a reçus, ni de quel type. C'est le format qui sert de contrat : chaque % annonce un argument et son type.

Pour lire ces arguments, <stdarg.h> fournit un type et quatre macros :

ÉlémentRôle
va_list ap;Le « curseur » : une variable qui retient où tu en es dans les arguments.
va_start(ap, dernier)Place le curseur juste après le dernier paramètre nommé de ta fonction (ici, le format).
va_arg(ap, type)Renvoie l'argument suivant, lu comme un type, et avance le curseur.
va_copy(dst, src)Copie un curseur dans son état actuel, si tu dois parcourir les arguments deux fois.
va_end(ap)Ferme le curseur. Chaque va_start (ou va_copy) doit avoir son va_end.

Un exemple sans rapport avec ft_printf, pour voir les macros ensemble : une fonction qui additionne n entiers.

somme.c
// n : combien d'entiers suivent
int	somme(int n, ...)
{
	va_list	ap;
	int		total;

	va_start(ap, n);
	total = 0;
	while (n-- > 0)
		total += va_arg(ap, int);
	va_end(ap);
	return (total);
}
🧭

Ce que va_arg sait

  • →où en est le curseur : il avance d'une case à chaque appel ;
  • →le type que tu lui demandes, rien d'autre.
🕳️

Ce qu'il ne sait pas

  • →combien d'arguments ont été passés ;
  • →de quel type ils sont vraiment ;
  • →si tu es déjà passé après le dernier.

Trois règles découlent de là. On ne revient pas en arrière : un argument lu est consommé (à moins d'avoir fait un va_copy avant). Le type donné à va_arg est une promesse : si l'appelant a passé autre chose, le comportement est indéfini. Enfin, les petits types sont promus : un char ou un short passé à une fonction variadique arrive comme un int (et un float comme un double). Pour %c, tu lis donc un int.

Suis le curseur dans la démo. Chaque conversion appelle va_arg et fait avancer ap d'une case. Puis clique sur « Mauvais type » : on demande %s alors que l'argument est un entier.

Démo : une file d'arguments et un curseur ap. Avec le format %c%s%d et les arguments A, hi, 7, chaque conversion lit une case et avance : la sortie est Ahi7 et la valeur de retour 4. Si on demande %s sur l'entier 42, va_arg lit 42 comme une adresse : le comportement est indéfini (souvent un segfault).

⚠️

Passer la va_list à une sous-fonction. Dès que tu découpes ton code, tu seras tenté de passer ap à une autre fonction. Le standard C dit qu'après un va_arg fait là-bas, la valeur de ap chez l'appelant est indéterminée. Sur Linux x86-64 le curseur avance quand même (la va_list y est un tableau, donc passée par adresse). Sur d'autres plateformes, dont macOS sur puce Apple, l'appelant ne voit rien avancer et relit la même case. Deux solutions portables : passer un pointeur sur la va_list (va_list *, puis va_arg(*ap, …)), ou garder tous les va_arg dans la fonction qui possède la liste.

04

Parcourir le format

Tu lis le format caractère par caractère, avec deux modes. Ce qui compte, c'est de savoir dans lequel tu es.

✍️

Mode texte

  • →Le caractère n'est pas %.
  • →Tu l'écris tel quel avec write.
  • →Tu comptes 1 caractère.
🔀

Mode conversion

  • →Tu viens de lire % : le caractère suivant est le spécificateur.
  • →Tu choisis l'action d'après lui (c s p d i u x X %).
  • →Tu lis l'argument avec va_arg (sauf pour %%) et tu l'écris.
  • →Tu ajoutes au compteur ce qui a été écrit, puis tu sautes les deux caractères.
pseudo-code
pour chaque caractère c du format :
    si c n'est pas '%' :
        écrire c ; compteur + 1
    sinon :
        s = le caractère suivant
        // une action par s : c s p d i u x X %
        compteur + ce qui est écrit
        avancer d'un cran de plus

La valeur de retour se construit en additionnant. Une bonne habitude : que chacune de tes petites fonctions d'affichage renvoie le nombre de caractères qu'elle a écrits, plutôt que de laisser la fonction principale les recompter. Tu additionnes ensuite ces retours et tu renvoies le total à la fin.

🧩

Choisir l'action. Pour passer du spécificateur à la bonne fonction, tu peux enchaîner des if / else if, ou ranger les fonctions dans un tableau. Relis la Norme avant de choisir : switch et for y sont interdits. Pour l'opérateur ternaire, selon la version de la Norme il est interdit ou limité aux cas simples non imbriqués : vérifie la Norme en vigueur.

Teste la lecture dans la démo : tape un format et ses arguments (séparés par |), puis avance pas à pas. Le cas préchargé est %d items%%\n avec 42. Essaie aussi %s avec NULL, %c avec \0, ou un % tout seul à la fin du format.

Démo : le format %d items%%\n avec l'argument 42. Chaque caractère est classé « littéral » ou « conversion » : %d consomme l'argument et écrit 42 (2 caractères), " items" est copié tel quel (6), %% écrit un seul % (1), le \n final compte 1. La sortie est 42 items% suivie d'un saut de ligne, et la valeur de retour est 10.

05

Afficher dans une base

Afficher un nombre, c'est le découper en chiffres. Dans une base b, le dernier chiffre est n % b et le reste du nombre est n / b. Problème : tu obtiens les chiffres à l'envers, alors qu'il faut écrire le premier d'abord. Sans malloc, il y a deux façons de s'en sortir : écrire d'abord n / b (récursion) puis le dernier chiffre, ou remplir un petit tableau local de la fin vers le début avant de l'écrire.

ConversionLitBase et chiffres
%d %iint10 : 0-9, avec - devant si négatif
%uunsigned int10 : 0-9
%xunsigned int16 : 0-9 puis a-f
%Xunsigned int16 : 0-9 puis A-F
%pvoid *16 : 0x, puis 0-9 et a-f
🔁

Le même nombre, plusieurs lectures. En mémoire, -1 est un entier de 32 bits qui ne contient que des 1. %d lit ces bits en complément à deux et donne -1 ; %u les lit comme un entier positif et donne 4294967295 ; %x donne ffffffff. Rien n'est converti : ce sont les mêmes bits, relus. C'est pourquoi %u, %x et %X lisent un unsigned int.

Trois détails à ne pas rater. Le zéro : 0 s'écrit 0, donc ta fonction doit toujours écrire au moins un chiffre. Le signe : pour %d, si n est négatif, tu écris - puis la valeur absolue (attention à INT_MIN, voir les pièges). Le pointeur : sur les machines 64 bits (Linux, macOS), un pointeur fait 64 bits. Range-le dans un unsigned long avant de le convertir en base 16, sinon tu coupes l'adresse. Le préfixe 0x s'écrit à part, et le pointeur nul demande un traitement spécial.

Entre un entier et choisis une conversion. Tu vois les 32 bits, les lectures possibles, les divisions successives et la sortie. À essayer : -1 en %u, %x et %X, 255 en %x, et 0 en %p, avec les deux libc.

Démo : un entier signé 32 bits et une conversion. Les mêmes 32 bits donnent -1 en %d, 4294967295 en %u, ffffffff en %x et FFFFFFFF en %X. 255 en %x donne ff. Pour %p avec un pointeur nul, glibc (Linux) affiche (nil) et la libc de macOS affiche 0x0 : ce cas dépend de la libc.

Étape par étape

1Prépare l'outillage. Un ft_printf.h (le prototype, <stdarg.h>, <unistd.h>), un Makefile qui range les objets dans libftprintf.a avec ar rcs, et une main de test que tu gardes hors de la bibliothèque. Fais compiler une ft_printf vide avec les flags du sujet.
2Écris le texte seul. Un affichage d'un caractère qui renvoie ce qu'il a écrit, et la boucle qui parcourt le format. Sans aucun %, ta fonction doit déjà afficher le bon texte et renvoyer la bonne valeur.
3Ajoute %c, %s et %%. C'est là que va_start, va_arg et va_end entrent en jeu. Teste %s avec NULL (mets-le dans une variable char *s = NULL; : écrit en littéral, le compilateur le refuse avec -Wall -Werror) et %c avec 0.
4Ajoute %d, %i et %u. La conversion en base 10 d'abord, puis le signe. Teste 0, un négatif, INT_MAX et INT_MIN.
5Ajoute %x et %X. Même fonction que pour la base 10, avec une autre base et un autre alphabet. Teste 0, 255 et -1.
6Ajoute %p. Un pointeur dans un unsigned long, le préfixe 0x, puis le pointeur nul.
7Soigne les erreurs. Bonne pratique : si un write échoue, renvoie -1 plutôt qu'un total faux, comme le fait printf (vérifie dans ton sujet si c'est exigé). Vérifie aussi qu'un % en fin de format ne fait pas lire au-delà du \0.
8Compare avec le vrai printf, cas par cas. Sortie et valeur de retour, comme ci-dessous. Redirige les deux sorties vers des fichiers et compare-les avec diff pour voir les octets invisibles.
test.c
int	a = printf("%d items%%\n", 42);
int	b = ft_printf("%d items%%\n", 42);
// a et b valent 10, et les deux lignes affichées sont identiques
Makefile
$(NAME): $(OBJ)
	ar rcs $(NAME) $(OBJ)
🎁

Les bonus. Ils ne comptent que si tout le reste est parfait. Si tu les tentes, la forme d'une conversion devient %[flags][largeur][.précision]spécificateur : lis les flags, puis la largeur, puis la précision, et seulement après le spécificateur. Une petite structure pour stocker ce que tu as lu t'évitera de passer dix paramètres à chaque fonction.

07

Pièges classiques

⚠️

%s avec NULL. Le vrai printf affiche (null), six caractères qui comptent dans la valeur de retour. Si ton affichage de chaîne fait un strlen ou lit *s sans tester le pointeur, c'est un segfault. Teste d'abord, puis écris (null) à la place. Pour ton test, mets le pointeur nul dans une variable (char *s = NULL;) : printf("%s", NULL) écrit en littéral ne compile pas avec -Wall -Werror.

⚠️

%c avec le caractère 0. ft_printf("%c", 0) doit écrire un octet nul et renvoyer 1. Si tu passes par une chaîne ou un strlen, le \0 est pris pour une fin de chaîne et rien n'est écrit. Écris le caractère lui-même avec write. Pour voir l'octet : ./a.out | od -c.

⚠️

INT_MIN. -2147483648 s'écrit sur 11 caractères. Si tu fais n = -n sur un int, tu obtiens 2147483648, qui ne tient pas : c'est un débordement d'entier signé, donc un comportement indéfini. Convertis d'abord dans un type plus large (long), ou traite ce cas à part. Dans ton fichier de test, écris INT_MIN (de <limits.h>) et pas -2147483648 : ce littéral est un long, et -Wall -Werror refuse de le passer à %d.

⚠️

%p avec un pointeur nul. La libc décide : glibc (Linux) affiche (nil), celle de macOS affiche 0x0. Ce n'est ni la même sortie ni la même valeur de retour (5 contre 3). Compare avec le printf de la machine où tu seras évalué et choisis en connaissance de cause (la démo sur les bases montre les deux).

⚠️

Le %% compté deux fois (ou qui consomme un argument). Dans le format, %% occupe deux caractères, mais il n'en écrit qu'un et ne consomme aucun argument. Compter 2, ou appeler va_arg par réflexe, décale tout le reste. ft_printf("%d items%%\n", 42) doit renvoyer 10.

⚠️

-1 en %u (et en %x). ft_printf("%u", -1) affiche 4294967295, %x affiche ffffffff et %X affiche FFFFFFFF. Si tu lis l'argument avec va_arg(ap, int) puis que tu le passes à ta fonction de %d, tu affiches -1. Pire : un reste négatif donne un index négatif dans ta chaîne de chiffres. Lis un unsigned int.

⚠️

Un % en fin de format. Avec ft_printf("100%"), le caractère qui suit le % est le \0. Si tu sautes les deux caractères sans tester, tu lis après la fin de la chaîne. Le comportement est indéfini pour le vrai printf aussi : choisis ce que tu fais, mais ne plante pas.

⚠️

Une adresse tronquée. Ranger un pointeur dans un int ou un unsigned int perd les 32 bits de poids fort : sur une adresse de pile, tu affiches une valeur qui n'est plus la bonne. Utilise un unsigned long.

⚠️

va_arg(ap, char). Un char est promu en int quand on l'envoie à une fonction variadique : demander un char à va_arg est incorrect (le compilateur te le signale, et avec -Werror ça ne compile pas). Lis un int et convertis ensuite.

💡

Bonne pratique : la valeur de retour quand write échoue. write renvoie -1 en cas d'erreur (sortie fermée, disque plein…), et le C dit que printf renvoie alors une valeur négative. Si tu additionnes les retours sans les regarder, tu renvoies un total faux au lieu de -1. Propager le -1 jusqu'à ta fonction principale est plus sûr ; vérifie dans ton sujet si c'est exigé. Pour le provoquer : ./a.out >&- ferme la sortie standard (bash, zsh). Le vrai printf met sa sortie en buffer et ne s'en aperçoit qu'à l'envoi : ce test sert surtout à vérifier que ta fonction renvoie -1 sans planter.

08

Comment je l'ai fait

J'ai découpé le projet en petites fonctions qui font chacune une seule chose et renvoient toutes le nombre de caractères qu'elles ont écrits. La fonction principale parcourt le format : un caractère ordinaire part directement avec write, et un % suivi d'une des neuf conversions est confié à une fonction de dispatch, une simple suite de if sur le spécificateur. Les nombres s'écrivent par récursion, sans buffer ni malloc : d'abord les chiffres de poids fort, puis le dernier. %x et %X partagent la même fonction, seul l'alphabet change. Pour %p, j'écris 0x puis l'adresse en hexadécimal, lue dans un entier 64 bits, et je traite à part le pointeur nul. Je n'ai pas fait les bonus. Le Makefile assemble la bibliothèque avec ar.
