C project · Variadic functions

ft_printf

Recode printf: understand how a function receives a variable number of arguments, then how it prints them in decimal, in hexadecimal and as a pointer.

subject: ft_printf · libftprintf.a · c s p d i u x X % · -Wall -Wextra -Werror · Norm

01

The project in brief

You write an ft_printf function that imitates the libc's printf: it receives a format string followed by a number of arguments it does not know in advance, writes the result with write, and returns the number of characters written.

The work comes down to three ideas: reading a variable number of arguments (stdarg.h), walking through the format while telling plain text from conversions, then printing each value in the right base with write as your only tool. The rest (the Makefile, the libftprintf.a library) is tooling.

💡

Your referee is the real printf. The subject asks you to imitate printf: for each case, compare its output and its return value with yours.

03

Variable arguments

In the prototype int ft_printf(const char *, ...);, the three dots tell the compiler: “anything can follow”. It checks nothing, and nor does your function know how many arguments it received, or of what type. The format is the contract: each % announces an argument and its type.

To read these arguments, <stdarg.h> provides one type and four macros:

ElementRole
va_list ap;The “cursor”: a variable that remembers where you are in the arguments.
va_start(ap, last)Puts the cursor right after the last named parameter of your function (here, the format).
va_arg(ap, type)Returns the next argument, read as a type, and advances the cursor.
va_copy(dst, src)Copies a cursor in its current state, in case you need to go through the arguments twice.
va_end(ap)Closes the cursor. Every va_start (or va_copy) must have its va_end.

An example unrelated to ft_printf, to see the macros together: a function that adds up n integers.

sum.c
// n: how many integers follow
int	sum(int n, ...)
{
	va_list	ap;
	int		total;

	va_start(ap, n);
	total = 0;
	while (n-- > 0)
		total += va_arg(ap, int);
	va_end(ap);
	return (total);
}
🧭

What va_arg knows

  • →where the cursor is: it moves forward by one slot at each call;
  • →the type you ask for, nothing else.
🕳️

What it does not know

  • →how many arguments were passed;
  • →what type they really are;
  • →whether you have already gone past the last one.

Three rules follow. You cannot go back: an argument that was read is consumed (unless you made a va_copy beforehand). The type you give to va_arg is a promise: if the caller passed something else, the behavior is undefined. Finally, small types are promoted: a char or a short passed to a variadic function arrives as an int (and a float as a double). For %c, you therefore read an int.

Follow the cursor in the demo. Each conversion calls va_arg and moves ap forward by one slot. Then click “Wrong type”: we ask for %s while the argument is an integer.

Demo: a queue of arguments and a cursor ap. With the format %c%s%d and the arguments A, hi, 7, each conversion reads one slot and moves on: the output is Ahi7 and the return value is 4. If we ask for %s on the integer 42, va_arg reads 42 as an address: the behavior is undefined (often a segfault).

⚠️

Passing the va_list to a helper function. As soon as you split up your code, you will be tempted to pass ap to another function. The C standard says that after a va_arg performed there, the value of ap in the caller is indeterminate. On Linux x86-64 the cursor does advance (the va_list is an array there, so it is passed by address). On other platforms, including macOS on Apple silicon, the caller sees nothing advance and reads the same slot again. Two portable solutions: pass a pointer to the va_list (va_list *, then va_arg(*ap, …)), or keep every va_arg in the function that owns the list.

04

Walking through the format

You read the format character by character, with two modes. What matters is knowing which one you are in.

✍️

Text mode

  • →The character is not %.
  • →You write it as is with write.
  • →You count 1 character.
🔀

Conversion mode

  • →You have just read %: the next character is the specifier.
  • →You pick the action based on it (c s p d i u x X %).
  • →You read the argument with va_arg (except for %%) and write it.
  • →You add what was written to the counter, then you skip both characters.
pseudocode
for each character c of the format:
    if c is not '%':
        write c; counter + 1
    else:
        s = the next character
        // one action per s: c s p d i u x X %
        counter + whatever was written
        advance one more step

The return value is built by summing. A good habit: have each of your small printing functions return the number of characters it wrote, rather than letting the top-level ft_printf function recount them. You then add up these returns and return the total at the end.

🧩

Choosing the action. To go from the specifier to the right function, you can chain if / else if, or store the functions in an array. Reread the Norm before choosing: switch and for are forbidden there. The ternary operator is, depending on the Norm version, forbidden or limited to simple, non-nested cases — check the current Norm.

Try the parsing in the demo: type a format and its arguments (separated by |), then advance step by step. The preloaded case is %d items%%\n with 42. Also try %s with NULL, %c with \0, or a lone % at the end of the format.

Demo: the format %d items%%\n with the argument 42. Each character is classified as “literal” or “conversion”: %d consumes the argument and writes 42 (2 characters), " items" is copied as is (6), %% writes a single % (1), and the final \n counts 1. The output is 42 items% followed by a newline, and the return value is 10.

05

Printing in a base

Printing a number means cutting it into digits. In a base b, the last digit is n % b and the rest of the number is n / b. Problem: you get the digits backwards, while the first one must be written first. Without malloc, there are two ways out: write n / b first (recursion) and then the last digit, or fill a small local array from the end to the start before writing it.

ConversionReadsBase and digits
%d %iint10: 0-9, with - in front if negative
%uunsigned int10: 0-9
%xunsigned int16: 0-9 then a-f
%Xunsigned int16: 0-9 then A-F
%pvoid *16: 0x, then 0-9 and a-f
🔁

The same number, several readings. In memory, -1 is a 32-bit integer made only of 1s. %d reads those bits as two's complement and gives -1; %u reads them as a positive integer and gives 4294967295; %x gives ffffffff. Nothing is converted: these are the same bits, reinterpreted. This is why %u, %x and %X read an unsigned int.

Three details not to miss. Zero: 0 is written 0, so your function must always write at least one digit. The sign: for %d, if n is negative, you write - and then the absolute value (watch out for INT_MIN, see the pitfalls). The pointer: on 64-bit machines (Linux, macOS), a pointer is 64 bits wide. Store it in an unsigned long before converting it to base 16, otherwise you cut off part of the address. The 0x prefix is written separately, and the null pointer needs special handling.

Enter an integer and choose a conversion. You see the 32 bits, the possible readings, the successive divisions and the output. Things to try: -1 as %u, %x and %X, 255 as %x, and 0 as %p, with both libcs.

Demo: a signed 32-bit integer and a conversion. The same 32 bits give -1 as %d, 4294967295 as %u, ffffffff as %x and FFFFFFFF as %X. 255 as %x gives ff. For %p with a null pointer, glibc (Linux) prints (nil) and the macOS libc prints 0x0: this case depends on the libc.

Step by step

1Set up the tooling. An ft_printf.h (the prototype, <stdarg.h>, <unistd.h>), a Makefile that puts the objects into libftprintf.a with ar rcs, and a test main that you keep outside the library. Get an empty ft_printf to compile with the flags from the subject.
2Write plain text only. A function that prints one character and returns what it wrote, and the loop that walks through the format. With no % at all, your function must already print the right text and return the right value.
3Add %c, %s and %%. This is where va_start, va_arg and va_end come into play. Test %s with NULL (put it in a variable char *s = NULL;: written as a literal, the compiler refuses it with -Wall -Werror) and %c with 0.
4Add %d, %i and %u. The base 10 conversion first, then the sign. Test 0, a negative number, INT_MAX and INT_MIN.
5Add %x and %X. Same function as for base 10, with another base and another alphabet. Test 0, 255 and -1.
6Add %p. A pointer in an unsigned long, the 0x prefix, then the null pointer.
7Handle errors. Good practice: if a write fails, return -1 rather than a wrong total, as printf does (check in your subject whether this is required). Also check that a % at the end of the format does not make you read past the \0.
8Compare with the real printf, case by case. Output and return value, as below. Redirect both outputs to files and compare them with diff to see the invisible bytes.
test.c
int	a = printf("%d items%%\n", 42);
int	b = ft_printf("%d items%%\n", 42);
// a and b are both 10, and the two printed lines are identical
Makefile
$(NAME): $(OBJ)
	ar rcs $(NAME) $(OBJ)
🎁

The bonuses. They only count if everything else is perfect. If you attempt them, the shape of a conversion becomes %[flags][width][.precision]specifier: read the flags, then the width, then the precision, and only after that the specifier. A small struct to store what you have read will save you from passing ten parameters to every function.

07

Classic pitfalls

⚠️

%s with NULL. The real printf prints (null), six characters that count in the return value. If your string printing does a strlen or reads *s without testing the pointer, it is a segfault. Test first, then write (null) instead. For your test, put the null pointer in a variable (char *s = NULL;): printf("%s", NULL) written as a literal does not compile with -Wall -Werror.

⚠️

%c with the character 0. ft_printf("%c", 0) must write a null byte and return 1. If you go through a string or a strlen, the \0 is taken for the end of the string and nothing is written. Write the character itself with write. To see the byte: ./a.out | od -c.

⚠️

INT_MIN. -2147483648 takes 11 characters. If you do n = -n on an int, you get 2147483648, which does not fit: it is a signed integer overflow, hence undefined behavior. Convert to a wider type first (long), or handle this case separately. In your test file, write INT_MIN (from <limits.h>) and not -2147483648: that literal is a long, and -Wall -Werror refuses to pass it to %d.

⚠️

%p with a null pointer. The libc decides: glibc (Linux) prints (nil), macOS prints 0x0. Neither the output nor the return value is the same (5 versus 3). Compare with the printf of the machine where you will be evaluated and make an informed choice (the demo on bases shows both).

⚠️

The %% counted twice (or consuming an argument). In the format, %% takes two characters, but it writes only one and consumes no argument. Counting 2, or calling va_arg by reflex, shifts everything after it. ft_printf("%d items%%\n", 42) must return 10.

⚠️

-1 as %u (and as %x). ft_printf("%u", -1) prints 4294967295, %x prints ffffffff and %X prints FFFFFFFF. If you read the argument with va_arg(ap, int) and then pass it to your %d function, you print -1. Worse: a negative remainder gives a negative index into your string of digits. Read an unsigned int.

⚠️

A % at the end of the format. With ft_printf("100%"), the character after the % is the \0. If you skip both characters without testing, you read past the end of the string. The behavior is undefined for the real printf too: choose what you do, but do not crash.

⚠️

A truncated address. Storing a pointer in an int or an unsigned int loses the 32 high-order bits: on a stack address, you print a value that is no longer the right one. Use an unsigned long.

⚠️

va_arg(ap, char). A char is promoted to int when it is passed to a variadic function: asking va_arg for a char is incorrect (the compiler warns you, and with -Werror it does not compile). Read an int and convert afterwards.

💡

Good practice: the return value when write fails. write returns -1 on error (closed output, full disk…), and C says that printf then returns a negative value. If you add up the returns without looking at them, you return a wrong total instead of -1. Propagating the -1 up to your top-level ft_printf function is safer; check in your subject whether it is required. To trigger it: ./a.out >&- closes standard output (bash, zsh). The real printf buffers its output and only notices when it flushes: this test is mainly useful to check that your function returns -1 without crashing.

08

How I did it

I split the project into small functions that each do one thing and all return the number of characters they wrote. The top-level ft_printf function walks through the format: an ordinary character goes straight out with write, and a % followed by one of the nine conversions is handed to a dispatch function, a simple chain of if on the specifier. Numbers are written recursively, with no buffer and no malloc: the high-order digits first, then the last one. %x and %X share the same function, only the alphabet changes. For %p, I write 0x and then the address in hexadecimal, read into a 64-bit integer, and I handle the null pointer separately. I did not do the bonuses. The Makefile builds the library with ar.
