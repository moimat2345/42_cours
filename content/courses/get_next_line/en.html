01

The project in short

You write get_next_line: a function that, on each call, returns the next line of a file descriptor. Called in a loop, it reads a whole file line by line; when there is nothing left to read, it returns NULL. The subject presents it as a useful function to keep in your collection (you can add it to your libft once the project is validated) and as the moment to learn an important C concept: static variables.

Here is how a test program uses it. This main is not to be turned in: the subject encourages you to write your own tests, which are not graded.

main.c (your test, not turned in)
int	main(void)
{
	int	fd;
	char	*line;

	fd = open("file.txt", O_RDONLY);
	while ((line = get_next_line(fd)) != NULL)
	{
		printf("%s", line);	// the line already contains its \n
		free(line);		// the caller must free it
	}
	close(fd);
	return (0);
}

Three questions sum up the whole project. The rest of the course answers them one by one.

1Where do you keep what you read past the end of the line? read() reads blocks, not lines: it almost always goes past the end of the line. The surplus must survive until the next call.
2When do you stop reading? As soon as a \n is in what you have read, or when read() reports the end of the file or an error.
3Who frees what? The subject tolerates no memory leaks. Every allocation must be freed, on every path.

03

Why a static variable

A call to get_next_line returns a single line. But read() has no idea where your lines end: it reads a block of bytes, period. Almost always, that block contains the end of one line and the start of the next. You have read this surplus: it is no longer in the file, the descriptor has moved on. And lseek() is forbidden, so there is no going back. If you throw the surplus away at the end of the call, it is lost for good.

So you need a place where this “leftover” survives between two calls. An ordinary local variable disappears when the function returns. A global variable would solve the problem, but they are forbidden. The subject's answer: the static variable.

Local variable

  • •Created on every call of the function
  • •Destroyed at the return
  • •Indeterminate starting value until you initialize it

Static variable

  • •Created only once, it exists for the whole program
  • •Keeps its value from one call to the next
  • •Starts at zero (so NULL for a pointer) if you don't initialize it
  • •Visible only inside the function that declares it

A tiny example, unrelated to the project, to see the difference:

counter.c
int	counter(void)
{
	static int	n;	// is 0 on the first call, then keeps its value

	n++;
	return (n);
}
// counter() returns 1, then 2, then 3... Without static, n would restart from an indeterminate value on every call.
💡

What survives is the pointer. The text too, if it is on the heap. Your static variable will typically be a char * pointing to a string allocated with malloc: the string stays there as long as you don't free it, and the static variable is the handle that lets you find it again on the next call. So it is up to you to free this leftover, at the right time.

get_next_line.c (skeleton)
char	*get_next_line(int fd)
{
	static char	*stash;	// the leftover from previous reads (NULL at the start)

	// 1. fill the leftover until it contains a \n (or the end of the file)
	// 2. extract the line from it
	// 3. keep in the leftover only what follows the line
}

Where should you declare it? Inside the function. A static variable placed outside any function is visible to the whole file: an evaluator may judge it equivalent to a global variable.

04

read() and BUFFER_SIZE

read(fd, buf, count) (manual page man 2 read, header <unistd.h>) reads at most count bytes from fd and writes them into buf. Its return value matters:

read() returnsMeaningWhat you do
n > 0n bytes were read (sometimes fewer than requested)You append them to the leftover and check whether there is a \n
0End of fileText waiting? You return it as is. Nothing? NULL
-1ErrorYou free what you hold and return NULL

read does not put a '\0' at the end: your buffer is a block of bytes, not a C string. Allow one more byte than BUFFER_SIZE and terminate it yourself before calling a string function.

BUFFER_SIZE is the block size requested on each read(). It is not in your code: it comes from the compile command (-D BUFFER_SIZE=n) and your evaluators change it. Since the project must also compile without the flag, you give a default value in the header:

get_next_line.h
#ifndef BUFFER_SIZE
# define BUFFER_SIZE 42	// the default value is up to you
#endif

The method fits in one loop: as long as the leftover contains no \n, read a block and append it to the leftover. As soon as there is a \n (or read returns 0), you cut: the line is returned, what follows stays in static. Play with the demo below. The “file” is a simple string, and each click calls get_next_line once.

Demo (requires JavaScript): a text “file”, a BUFFER_SIZE slider from 1 to 16 and a button to call get_next_line. On each call, the demo shows every read(), the content of the static variable before and after, the line returned and the cumulative number of read() calls.

Example without JavaScript: file ab\ncd\nef (no final \n), BUFFER_SIZE=4.

Call 1. read reads "ab\nc", the function returns "ab\n", the leftover is "c".
Call 2. read reads "d\nef", returns "cd\n", leftover "ef".
Call 3. read reads 0 bytes (end of file), returns "ef", static goes back to NULL.
Call 4. read again reads 0 bytes, returns NULL.

What the demo shows you, to reproduce in your own code:

1The leftover bridges the calls. With the sample file and BUFFER_SIZE=4, the 1st call reads "ab\nc": it returns "ab\n" and keeps "c", which the 2nd call completes.
2A call may not read at all. Set BUFFER_SIZE to 16: the whole file arrives on the first call, then as long as the leftover contains a \n, the lines come out without any new read().
3With 1, everything works too, but slowly. As many read() calls as bytes: the “cumulative” counter climbs fast.
4The end is read in two steps. File without a final \n: a read() returning 0 makes the function return the last line, and the next call returns NULL. File ending with a \n: after the last line, the next read() returns 0 and the function returns NULL.
05

Step by step

A working order that avoids debugging everything at once. Splitting into functions is a suggestion, not a requirement: the subject only fixes the prototype and the files. Don't take it for a ready-made solution, every step is still yours to write.

1Set up the header. The prototype of get_next_line, an include guard, the includes you need (<stdlib.h> for malloc and free, <unistd.h> for read) and the default value of BUFFER_SIZE.
2Write your tools in get_next_line_utils.c. libft is forbidden: you only rewrite what you need. Typically the length of a string, the search for a character, the concatenation of two strings (into a new allocation) and copying a portion. The Norm limits the size of functions and their number per file: these small tools will help you stay within the limits. Test each one separately.
3Start with the safeguards. Negative fd: NULL right away. A BUFFER_SIZE value that makes no sense (zero, negative) also deserves a NULL rather than undefined behavior.
4Fill the leftover. Allocate a read buffer (with malloc, of BUFFER_SIZE + 1 bytes). As long as the leftover has no \n: read, terminate the block with a '\0' and append it to the leftover. If read returns 0, leave the loop. If it returns -1, free everything and return NULL. Free the read buffer on every exit.
5Extract the line. If there is a \n, copy up to it, \n included. Otherwise (end of file without a \n), copy everything that is left. If the leftover is empty or does not exist: nothing to return, so NULL.
6Recompute the leftover. What follows the \n becomes the new leftover (new allocation), then you free the old one. If nothing is left, don't keep an empty string alive: free it and set the pointer back to NULL.
7Test methodically. BUFFER_SIZE at 1, 2, 42, 9999, 10000000. Empty file, a single line without \n, only \n characters, a very long line. Standard input. An invalid descriptor. Run every test under valgrind (or leaks on macOS) to hunt leaks.

Bonus: multiple file descriptors. The bonus changes just one thing: instead of one leftover, you need one per descriptor, and the subject requires a single static variable. The common interpretation is that an array declared static counts as a single variable: you index it by fd. The subject does not say so in so many words: confirm it with your evaluator. Try the demo by alternating the two buttons, first with a single shared leftover, then with one leftover per descriptor.

Demo (requires JavaScript): two “files”, open on fd 3 and fd 4, and two buttons to call get_next_line(3) or get_next_line(4) in alternation. Two modes: a single leftover for all descriptors, or one leftover per descriptor.

Example without JavaScript: fd 3 contains a1\na2\na3, fd 4 contains b1\nb2\nb3, BUFFER_SIZE=4, calls in the order fd 3, fd 4, fd 3, fd 4.

A single shared leftover: "a1\n", "ab1\n", "b2\n", "a32\n". Only the first call is right.

06

Classic pitfalls

⚠️

BUFFER_SIZE = 1. One read per byte: your function must stay correct, and not absurdly slow. Beware of code that assumes several bytes per block, and of a search for the \n that restarts from the beginning of the whole leftover on every loop iteration.

⚠️

BUFFER_SIZE = 10000000. Never declare your read buffer as a local array: char buf[BUFFER_SIZE + 1] asks the stack for about 10 MB, more than its usual size (8 MB on many systems, ulimit -s). Result: segfault, so 0. Allocate it with malloc and free it.

⚠️

File without a final \n. The last line has no \n: you still return it, as is, then NULL on the next call. Don't lose it, and don't add one of your own: the subject is precise on this point.

⚠️

A line that starts with \n. An empty line in the file is the string "\n": one character, not an empty string. A test like “if the line is empty, it's the end” makes you lose the empty lines. Only NULL signals the end.

⚠️

Returning "" at the end instead of NULL. At the end of the file, you return NULL, not an allocated empty string. With "", a while (line) loop would never stop, and each allocated empty string would be one more leak.

⚠️

read() returns -1. Invalid or closed descriptor, directory opened instead of a file: read fails and returns -1 (this is the case for -1, for a descriptor that is not open and for a directory). Test < 0 explicitly: a while (read(...)) loop treats -1 as “keep going”. On error, free the leftover and the buffer, then return NULL. The subject asks for this on any error.

⚠️

Leaks, in the three classic places. The read buffer (to free on every exit, errors included), the old leftover (to free as soon as a new one replaces it) and the final leftover (to free and set back to NULL as soon as the last line has gone). The returned line belongs to the caller. Also think about malloc failing: every path must free what it holds.

⚠️

Concatenation that copies everything. If, for each block read, you copy the whole leftover into a new string, and if, for each line returned, you copy everything that follows, a large file or a very long line costs quadratic time. With a big BUFFER_SIZE, the leftover is huge from the first read, and each returned line copies almost all of it. Avoiding these copies is an optimization, not a requirement of the subject. To see where you stand, don't use an absolute duration: on the same file of 100 to 500 KB, compare BUFFER_SIZE=1 and BUFFER_SIZE=10000000 with a reasonable BUFFER_SIZE such as 42. With 1, even linear code stays slow (one system call per byte): what should alert you is a running time that blows up when you double the size of the file. Look for the \n only in the last block added.

⚠️

Standard input. The subject requires it to work with get_next_line(0) too. Test with a redirection (./a.out < file), with a pipe (printf 'a\nb' | ./a.out) and at the keyboard (Ctrl-D at the start of a line sends the end of file). At the keyboard, read returns at most one line at a time, even with a large BUFFER_SIZE: your code must never assume that read fills the buffer.

⚠️

Bonus: an fd outside the array. A negative or too large fd writes outside the array of leftovers. Check the index before touching it. And remember: a single static variable, not one per descriptor (an array counts as one, according to the common interpretation; the subject does not specify it, check with your evaluator).

07

How I did it

I kept all the text that was read but not yet returned in a single static variable: a pointer to an allocated string. On each call, a first function reads blocks of BUFFER_SIZE bytes into a temporary buffer and appends them to the leftover until it sees a \n or the end of the file. A second one copies the line, \n included. A third one builds the new leftover and frees the old one; at the end of the file, everything is freed. This split fits within the Norm and can be tested piece by piece. If read fails, I free the leftover and return NULL. For the bonus, I kept the same functions: the static variable becomes a fixed-size array of pointers, indexed by the descriptor, so each file finds its own leftover again.
